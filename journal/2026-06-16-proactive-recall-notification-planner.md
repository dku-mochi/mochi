# 능동 회수 알림 — "언제/어떻게 보내나" 실데이터 결정 (2026-06-16)

> 코드 변경 없음 — `lab/` 실험 3건 + 본 journal + CHANGELOG/.gitignore 만. 프로덕션·committed 문서 정합 반영은 아직(§8). 06-15 proactive-recall 시리즈의 **연속**으로, 앞 4 journal이 "무엇을/어디서" 정했다면 이 세션은 **"언제/어떻게 보내나"를 실데이터로** 정한다.

---

## 0. TL;DR

선행 journal들이 능동 회수의 트랙·UX·notification 방향을 정했으나, **"알림을 정확히 언제·어떤 계획으로 보내나"**가 비어 있어 이 세션이 시작됐다. 추측 대신 **실데이터(최다 보유 계정 114건)로 3개 실험**을 돌려 결정했다.

1. **"저장시각 = 알림 받기 좋은 시각" 가설 폐기.** 저장은 능동(내가 폰 보다 캡처)·알림은 침입(모찌가 밀어넣음)이라 환영도가 다르다. 데이터가 주는 건 "환영 시각"이 아니라 **"묻히지 않을 시각"(깨어있음)** + **"확실히 피할 시각"(6~10시 공백)**.
2. **importance 단독 무게게이트 폐기** — importance가 무게와 **직교**(같은 imp 안에 토익=heavy·과제=light 공존). intent_type이 훨씬 나은 1차 신호.
3. **알림 = "LLM 플래너 + 규칙 집행가드" 하이브리드.** LLM이 계획을 *제안*, 규칙이 가드를 *강제*. "LLM이 다"도 "규칙이 다"도 아님.
4. **맥락주입(sliding window)의 진짜 가치는 비결정성 감소가 아니라 "조율"** — A/B 실험에서 강프롬프트+맥락주입(B)이 죽은시간 배치 0(vs 34)·난사 절반(max 7 vs 13)·마감없는 의도에 주기넛지 자동생성으로 운영품질 압승. 단 비결정성 자체는 측정설계 결함으로 미결.

## 2. 실데이터 추출 + 시간대 분석 (`lab/data/recall-dump/`)

최다 보유 계정(`71503fa8…`, **114건** = active 103/soft-del 11) 전체를 read-only로 추출(mochi_items·intent_instances·entities·embeddings chunk_text·conversations·messages). 약 1주치(06-09~06-15).

**핵심 발견:**
- **시간대(KST, 저장시각)**: 0~5시 **49%**, **6~10시 0%**(채팅도 동일 공백), 11~17시 30%, 18~23시 21%. 야행성(개발자+학생).
- **6~10시 죽은시간**이 저장·채팅 양쪽에서 일치 → 이 사용자에게 아침 알림은 묻힌다. 황금시간 = 밤 22~새벽3 + 낮 13~17.
- **트랙 B 데이터 풍부**: 미래 마감/일정 19건(과제·신청마감·시험·여행). 마감 시각이 거의 다 `23:59`("그날까지" — 23:59 알림은 이미 늦음).
- channel screenshot 80.7%, intent memo 68.6%/todo 19.8%/schedule 6.6%/knowledge 5%.

> **가설 반증**: "저장시각=알림 좋은 시각"으로 출발했으나 틀림. 저장 피크(새벽2시)에 push=수면방해. 데이터는 "묻히지 않을 시각"과 "피할 시각(6~10시)"만 준다. 진짜 답은 고정 시간표가 아니라 **개인 활동시간 학습 → 죽은시간 회피**(이건 일반화됨).

## 3. 실험① 무게 판정 (`lab/active/recall-notification-weight/`)

질문: 일정의 무게(→단발 vs D-7/3/1 다단)를 기존 `importance`(1~5)만으로 정할 수 있나? (규칙 vs flash-lite, 미래 마감/일정 26건)

**결론: importance 단독 불충분 — 확정.**
- **importance가 무게와 직교**: imp5 안에 토익(heavy)·과제(light) 공존, imp3 안에 여행(heavy)·민수만남(light) 공존. 같은 importance가 정반대 무게.
- **분포 쏠림**: 날짜 있는 항목이 거의 다 imp5(5=17, 1~2=0) → imp 규칙은 light 자체를 못 만듦(분별력 상실). 분석 LLM이 "마감 있으면 중요"로 매긴 탓 — importance는 *시간압박* 반영이지 *리드타임 길이*가 아님.
- **LLM 추가가치 실재**: title 의미로 "과제 todo=가벼움 / 시험·여행 schedule=무거움"을 importance와 다르게 가름.
- 단 flash-lite 흔들림(같은 과제에 light↔medium) + 과거건 오판(마감지난 것도 heavy).

**결정**: 무게 = `intent_type 1차 분기`(todo 마감형=규칙 D-1+days_until / schedule 일정형=LLM) + `importance는 보조 타이브레이커만` + 전처리 가드(과거/완료 제외, 중복 mochi_item 1회).

## 4. 실험②③ 알림 플래너 (`lab/active/recall-notification-planner/`)

송준서가 비전을 확장: **알림 계획 전체(시점들·주기·상대시간·멘트)를 LLM 플래너가 짠다.** 든 케이스가 §3 분류를 일부 깸 —
- "엄마에게 전화"(마감없는 todo)·"월급 옷"(위시)은 deadline이 없어 D-1 규칙 무의미 → **주기 넛지**(3일×2~3, 10일×3) 필요, 의미판단이라 LLM.
- 과제 마감은 **상대시간**("4시간 전 저장 → 2시간 후 알림").
- 당일/긴급 제외 **하루 2건 cap**, 같은 날 **묶기**, 반응학습으로 멘트·시각 수정.

**송준서 교정 2개(설계를 끈 축):**
- **교정A**: "sliding window만 하면 안 된다 — 초기 결정이 이후로 전파되니, 처음부터 잘 나오게 **하네스(프롬프트)를 세게 쪼여라**." → 강한 규칙 프롬프트 + 시간순 맥락주입을 한 쌍으로.
- **교정B**: "exact 매칭 채점 말고 **LLM-as-judge**. gold=7일전·실제=10일전이면 의도(다단 점층) 같으니 맞는 것." (이번 실험은 rule-based verdict라 §7-3에 judge 정밀화 후속.)

### A/B 실험 (38케이스 = 실데이터 active + gold 7합성, flash-lite temp=0, 152콜)
- **A** = 약한 프롬프트 + 독립 호출
- **B** = 강한 규칙 프롬프트(50일내 D-3/7/15/30·먼미래 10일간격·전날무조건·하루2~3cap·묶기·24h예외·클릭안함≠negative) + 시간순 이전결정 맥락주입

**결과:**

| 지표 | A | B | 판정 |
|---|---|---|---|
| 순서셔플 exact match | **1.0** | 0.053 | ⚠️ 측정 아티팩트(아래) |
| 죽은시간(6~10시) 배치 | 34 | **0** | **B 압승** |
| 하루 최대 알림 | **13**(난사) | 7 | B 우세 |
| gold7 O/△/X | 3/3/1 | **5/1/1** | B 우세 |
| 초기 6건 reasonable | — | **6/6** | 전파 위험 낮음 |

1. **비결정성 숫자는 오해** — 셔플 측정이 맥락주입에 부당하다. A는 독립이라 셔플해도 입력 불변(1.0). B는 순서가 바뀌면 주입 맥락이 바뀌어 결과가 다른 게 **설계상 당연**(=순서민감성, ≠불안정). 실운영은 시간순 고정이라 안 나타남. **부수 발견**: temp=0 독립(A)이 1.0 = "비결정성이 애초에 큰 문제였나"를 재검토할 거리(단 무게실험의 흔들림과 상충 → 같은 순서 N회 재측정 필요).
2. **운영품질은 B 압승** — 강프롬프트+활동히스토그램이 죽은시간 완벽 회피(0), 난사 절반. **맥락주입의 가치는 비결정성이 아니라 "조율"**(난사방지·묶기·기존알림 회피)에서 나옴 = 원래 목표보다 더 쓸모.
3. **gold: 마감없는 의도에 주기넛지 자동생성 성공** — G6 엄마전화(B=O, 7일 repeat)·G7 코트(B=O, 20일 repeat). "AI가 이 판단 하나?"=된다.
4. **B 부작용**: G5 기말고사를 "이미 알림 밀집"이라 단발로 깎음(X). 맥락주입이 "최소화"로 과작동해 **중요한 걸 희생** → "중요도 우선" 가드 필요(§7-2).

## 5. 확정 설계 — 알림 = LLM 플래너 + 규칙 집행가드

**구조 (notification-decision의 hook produces/cron decides를 구체화):**
- **hook produces (생성시점, LLM 플래너)**: 강한 규칙 프롬프트 + 개인 활동 히스토그램 + 시간순 이전결정 맥락 주입 → 구조화 출력 `{notifications:[{date,time,content,repeat_rule}]}`.
- **cron decides (발송직전, 규칙가드)**: 하루 cap·야간무음·dismiss 영구존중·묶기·**중요도 우선**·stale/완료 재평가.

**결정 축 (이 세션이 채운 빈칸):**

| 결정 축 | 누가 | 근거 |
|---|---|---|
| **시각**(몇 시) | 개인 활동 히스토그램 규칙 (없으면 10~20시) | 추출: 6~10시 공백 |
| **무게**(스케줄 강도) | todo=규칙 / schedule=LLM / importance=보조 | 실험① 직교 실증 |
| **계획**(시점들·주기·상대시간) | LLM 플래너 (강프롬프트, 마감없는 건 주기넛지) | 실험②③ |
| **보낼까+문구** | LLM (가드 안에서) | notification-decision |
| **하드가드**(야간·cap·dismiss·묶기·중요도우선) | 규칙 | 실험③ B부작용 |
| **비결정성 통제** | 강프롬프트 + 시간순 맥락주입 | 실험③ (단 재측정 필요) |

**신호 원칙**: 클릭=양성만(클릭 0을 페널티로 쓰지 않음 — "안 누름≠부정", 알림 보고 바로 행동한 경우 많음). 부정은 명시적 dismiss + lifecycle 완료(archived). `item_access_log`의 "직접 열어봄"이 클릭보다 신뢰도 높은 양성.

## 6. 임베딩 타이밍 (송준서 답 — 아키텍처, 추후 선택)

생성 시점엔 임베딩이 아직 없을 수 있다 → 2버전:
1. **쉬운 버전**: 생성 후 임베딩 저장 → 결과가 todo/schedule이면 push 관리 에이전트 호출 → 멘트·시간·날짜 생성.
2. **세심한 버전**: 생성 시점 메인 에이전트가 push 예약 여부 결정 → push 에이전트가 분석 후 시간·멘트 생성 → worker 발송. (memo/knowledge도 "after_30d_reminder"처럼 가능.)

이번 실험은 이미 임베딩된 데이터를 써서 이 선택과 무관. 플래너 검증 후 결정.

## 7. 미해결 / 후속

1. **비결정성 깨끗 재측정** — 순서 셔플 말고 **같은 시간순 N회 반복** + control(강+독립)로 "강프롬프트 vs 맥락주입" 분리. temp=0 독립이 1.0이라 전제 재검토.
2. **"중요도 우선" 가드** — G5 기말고사 같은 희생 방지(묶기·최소화가 중요한 걸 못 깎게).
3. **judge 채점** — 현 rule-based verdict는 "7일전 vs 10일전"을 깎음(토익 △). LLM-as-judge(rubric: 점층구조/주기넛지/난사방지/시각/전날)로 정밀화.
4. **임베딩 타이밍 2버전** 중 선택(§6).
5. **학습 루프(반응→멘트·시각 수정)·알림 묶기 구현** = notification 가동 후(반응 로그 콜드스타트, 지금 데이터 0).
6. **표본 한계** — 1명·1주·야행성. 일반화 금지. 2·3위 계정(43·26건)으로 활동시간·"todo=가벼움/schedule=무거움" 교차검증.
7. **상대시간 트리거**(마감-Nh)·**반복 알림(repeat_rule)**의 발송 인프라 — tech-design §5 새 빌더에 포함.
