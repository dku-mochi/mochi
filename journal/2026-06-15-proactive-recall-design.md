# 능동 정보 회수 기획 — 2026-06-15

## 0. TL;DR (한 화면 요약)

채팅의 알림 예약을 넘어, **저장된 기록이 시간·맥락 조건을 충족하면 모찌가 먼저 안부를 건네는** 능동 정보 회수 기능을 기획했다. 미션("필요한 기억은 *떠오른다* — 주체는 모찌")의 시간 축 구현이다.

이번 토론의 **결정적 발견 세 가지**:

1. **30/180일 단일 규칙은 폐기한다.** 진짜 죄는 임의의 매직 넘버가 아니라, **저장 동기가 다른 세 트랙을 하나로 뭉갠 것**이다.
2. **저장 동기 → 회수 전략은 3트랙으로 갈린다** (송준서 본인 경험에서 도출):
   - **학습 비축(지식)** → 시간 기반 능동 푸시(spaced repetition). 단 **추출 + LLM 사전 정리가 선결** — 회수를 "다시 보기"에서 "정착(떠올림)"으로 격상.
   - **망각 방지(할일·스케줄)** → 마감 역산 단발 알림. ≈ 이미 해결됨.
   - **혹시 몰라 비축(아카이브)** → **시간 알림이 아니라 맥락 소환.**
3. **아카이브형에 시간 알림(30일이든 spaced든)을 쏘는 건 근본적으로 틀렸다.** "언젠가 필요할 때"의 "필요할 때"는 시계가 아니라 사용자의 현재 맥락이 정한다.

기술적으로 능동 회수는 **기존 outbox 워커와 분리된 가벼운 cron 트랙**이면 분석 throughput에 병목 0. pub/sub은 능동 회수엔 불필요(저지연 무관).

## 1. 왜 이 기능인가 — 출발점은 "기능"이 아니라 "왜 저장하는가"

발단은 "채팅의 알림 예약을 AI가 스크린샷을 분석해 능동적으로 쏴주면 어떨까"였다(예: *내일 민수님과 약속 잊지 않으셨죠?*, *한 달 전 저장한 RAG 까먹지 않으셨죠?*, *구매 고민하던 마우스 사셨나요?*).

이건 미션 정중앙이다 — 회수의 능동 주체가 사용자가 아니라 모찌(`PRODUCT.md §1.5`). 하지만 기능 나열로 출발하면 30/180일 같은 임의 규칙으로 빠진다. 그래서 **"송준서는 왜 기록을 하는가"** 부터 다시 봤고, 거기서 전체 아키텍처가 나왔다.

### 송준서의 저장 동기 (원본 — 기획의 토대)

- **지식**
  - 설명 영상 캡처 → "나중에 봐야지, 지금 보긴 귀찮은데 도움될 듯" → 저장. *영상은 설명 정보를 가져오기 어렵다.*
  - 설명 medium(아티클) → "보면 좋을 듯". *앱이 부분 정리는 하지만 URL 추출 실패하면 무효용.*
  - **고통: 나중에 안 본다.**
- **할일 / 스케줄**
  - 까먹을까봐 = 단발성.
  - 과제 → 2일 전 알림이 좋다 / 민수와 약속 → 1일 전 / 대회 날짜 → 지속적 인지 필요.
  - 원래 캘린더·리마인더에 직접 박아야 했던 문제 → **우리가 어느 정도 해결함.**
- **기록(쇼핑·영상·친구 채팅·인스타 캡처 등)**
  - "언젠간 필요할 정보일 듯" → 저장. **그러고 정작 필요할 때 못 찾거나 안 본다.**

## 2. 핵심 모델 — 저장 동기가 회수 전략을 결정한다

| 저장 동기 | 사용자 심리 | 회수 실패 양상 | 트리거의 본질 | 올바른 회수 전략 |
|---|---|---|---|---|
| **학습 비축**(지식) | "미래의 나에게 유용, 지금은 귀찮" | **영영 안 봄** | **시간** | 모찌가 끌고 와야 함 → spaced repetition (추출 선결) |
| **망각 방지**(할일·스케줄) | "까먹으면 큰일" | 까먹음 | **마감(고정 시각)** | 마감 역산 단발 알림 (≈ 이미 해결) |
| **혹시 몰라 비축**(아카이브) | "언젠가 필요할 듯" | **필요한 순간 못 찾음** | **맥락**(시계 아님) | 시간 알림 ❌ → 맥락 소환 |

> **30/180 단일 규칙의 죄 = 이 3트랙을 한 상수로 뭉갠 것.** 특히 아카이브형을 시간 알림으로 다룬 게 가장 큰 오류고, 지식형은 타이밍 이전에 추출이 막혀 있다.

## 3. 3트랙 회수 아키텍처

```
학습 비축(지식)     → [추출 선결] → 시간 기반 능동 푸시 (spaced repetition)
망각 방지(할일/일정) → 마감 역산 알림. 무거운 건 점점 촘촘하게. (≈ 해결됨)
혹시 몰라(아카이브)  → 시간 알림 아님. 맥락 재등장 시 자동 소환 + 저장 시 연관 강화.
```

### 트랙 A — 학습 비축(지식): 추출 선결 → spaced repetition

**A-1. 선결 조건: 추출(가장 중요).**
영상 캡처가 썸네일+제목만 남으면, 3일 뒤든 30일 뒤든 회수해봐야 *"이게 뭐였더라"* 인 빈 껍데기다. 송준서가 두 번 짚은 고통("영상은 정보 가져오기 힘듦", "URL 추출 안 되면 무효용")이 회수 기능의 발목이다.

- 회수의 전제 = **회수할 알맹이의 존재.** 영상 → 자막/스크립트, medium → 본문 추출.
- **추출 성공 여부 = 회수 우선순위.** 알맹이 없는 항목을 끈질기게 회수하면 그게 스팸이다. 추출 실패 항목은 회수에서 빼거나, 추출 재시도를 먼저.

**A-2. spaced repetition (30/180 대체).**
지식의 본질은 "한 번 알리고 끝"이 아니라 **잊을 때쯤 반복해서 떠올려줘야 정착되는 것**(에빙하우스 망각곡선; Anki·Readwise 방식).

```
저장 → 3일 후 "이거 봤어요?"
  ├─ 봤다/도움됐다 → 다음 간격 ×N (예: 3일 → 7일 → 18일 → 45일 …)
  └─ 관심없다       → 빠르게 소멸(archive)
```

- 회수할 때마다 간격을 늘린다. **이게 미션과 가장 정확히 맞는다** — 단발 알림이 아니라 기억을 *정착*시키니까.
- **재방문 신호로 보정**: 자주 열어본 항목은 이미 안 잊으므로 회수 불필요. *안 본 것일수록 회수 가치 ↑.* 회수는 "오래된 것"이 아니라 "잊혀가는데 가치 있던 것"에 한다. (이 재방문 신호는 `item_access_log`로 데이터 확보 — 송준서 결정으로 MVP 포함, 기술문서 §2.4.)
- 구체적 간격 공식(FSRS/SM-2 등)은 미확정 — §9 참고.

**A-3. LLM 사전 정리 층 (송준서 제안 — spaced repetition의 사실상 전제).**
지식 저장의 고통은 두 겹이다: (a) **나중에 안 본다**(타이밍 → A-2가 해결), (b) **봐도 부담이다**(영상 10분·아티클 길다 — "지금 보긴 귀찮아서" 저장). A-2만으로는 (b)를 못 풀어, 잊을 때쯤 다시 보여줘도 *또 부담*이라 사용자가 결국 "그만"을 누른다. → 추출(A-1) 위에 **LLM이 미리 정리(요약·구조화)하는 층**을 얹어 회수를 *다시 보기*에서 *정착(떠올림)*으로 격상한다.

| | 정리 없이 | 사전 정리 후 |
|---|---|---|
| 회수 카드 | "저장한 강의 다시 보세요"(또 10분) | "핵심은 이거였어요(3줄). 기억나세요?" |
| 회수 비용 | 높음 → 또 미룸 → 안 봄 | **0에 수렴** → 원본 안 봐도 회수 |
| 성격 | 다시 보기 | **마이크로러닝(정착)** |

설계 결정:
- **신규 아님 — 확장**: 분석 파이프라인이 이미 `summary`(1–2문장)·`category`·`entities` 추출. 사전 정리는 이 summary를 *지식 한정으로* 더 깊게(핵심 bullet·구조·"이 자료의 쓸모") 뽑는 것. 한계비용 작음(같은 LLM 콜 안).
- **정리 시점 — 절충**: 저장 시 *가벼운* 정리(기존 summary 강화), 회수 카드를 펼칠 때 *깊은* 정리(실제 관심 신호 확인 후, 지연 감수). 전량 즉시 깊은 정리는 비용 낭비.
- **자료 종류별 형태**: 강의 → 핵심 개념, how-to → 단계, 아티클 → 주장+근거. 한 틀로 뭉개지 않음.
- **순서**: `추출(A-1) → 정리(A-3) → spaced 회수(A-2)`. 추출 실패 → 정리 불가.

가드(시니어 관점):
- **원본 대체 금지** — 정리는 회수의 미끼·요약이지 원본(영상 전체)의 대체물이 아님. 원본 링크 항상 보존.
- **정확도 = 학습 위험** — 틀린 요약은 *잘못된 기억을 정착*시킴(학습 자료라 특히 위험). 출처 명시·원본 우선·과한 단정 회피.
- **비용은 깊이로 조절**(flash-lite; 저장 시 얕게 / 회수 시 깊게).

> **기존 코드 사실**: `knowledge` lifecycle(30일→decaying, 180일→reviewRequested)은 **이미 구현돼 있다**(`lifecycle_policy.py`, `DOMAIN_DESIGN.md §5`). 단 이건 상태 전이만 하고 *발송 경로가 없다*. 즉 "고정 컷오프 → 적응형 spaced"로 바꾸고 발송을 연결하는 작업.

### 트랙 B — 망각 방지(할일·스케줄): 마감 역산

송준서 말대로 대체로 해결됐다(`schedule.payload.date/time`, `todo.payload.deadline` 추출됨). 얹을 것:

- **마감 역산 간격은 유형마다 다르다**: 과제 D-2, 약속 D-1 등. 사용자 지정 또는 유형별 기본값.
- **"단발 vs 반복"은 intent로 안 갈리고 항목의 무게로 갈린다.** "대회 날짜 = 지속적 인지"는 schedule인데도 반복이 필요한 케이스 → 멀고 무거운 건 **D-30/D-14/D-7/D-3** 식으로 점점 촘촘하게.
- 이 트랙이 **유일하게 즉시성(푸시)이 본질적으로 정당**한 트랙이다(놓치면 의미 소멸).

### 트랙 C — 혹시 몰라(아카이브): 시간 알림이 아니다 ★

**이번 토론의 가장 큰 깨달음.** "언젠가 필요할 때"의 **"필요할 때"를 모찌는 시계로 예측할 수 없다.** 인스타 맛집 캡처는 *30일 후*가 아니라 *내가 그 동네 갈 때* 필요하고, 친구 채팅 캡처는 *그 친구 만날 때* 필요하다.

→ 아카이브형에 시간 기반 알림(30일이든 spaced든)을 쏘는 건 근본적으로 틀렸다. 이건 *회수 타이밍* 문제가 아니라 **맥락 매칭** 문제다. 해법:

- **관련 맥락이 재등장할 때 자동 소환.** 또 마우스를 저장하면 *"지난번 고민하던 마우스는요?"* (`similar` 임베딩 이웃 인프라 — `GET /mochi_items/{id}/similar` 이미 있음).

**MVP 방향 (Claude×codex 3턴 합의 — 상세 기술은 `2026-06-15-proactive-recall-tech-design.md`):**
- **트리거는 "사용자가 방금 던진 현재 맥락"뿐** — ① 새 저장물(방금 저장한 것과 유사한 과거 archive) ② 채팅 질문(질문과 관련된 과거 기록). 위치·캘린더·행동예측은 MVP 제외(권한·스팸 위험).
- **푸시 절대 금지, 카드만** — 저장 직후 / 홈 "모찌가 챙기는 것" / 채팅 하단. false-positive 비용이 낮은 표면에만.
- **비교 후보 소환**: 쇼핑처럼 결정형은 *"지난번 마우스랑 같이 볼까요?"* — 새 스키마 없이 기존 `shopping_product` entity 재활용. 데모 임팩트 큼.
- **근거를 함께 표시**("저장한 내용 중 '…' 부분이 유사") — 왜 떴는지 설명. 소환 단위(item)와 설명 단위(chunk)가 다르다.
- **응답으로 학습**: 관련없어요(억제) / 다신 소환 안함(영구).

> **미션 긴장**: 검색은 "사용자가 *떠올린다*"(위반 경향), 자동 소환은 "모찌가 *떠오르게* 한다"(정합). 그래서 아카이브형의 정답은 *더 나은 검색창*이 아니라 *맥락 소환*이다.

## 4. 채널 정책 — 알림 피로가 이 기능의 성패다

**모든 회수를 푸시로 쏘면 스팸이 되고, 스팸은 앱 삭제로 이어진다(미션 위반급).** 시급성으로 채널을 나눈다.

| 시급성 | 채널 | 이유 |
|---|---|---|
| **시각 고정**(트랙 B: 약속·마감) | **푸시(APNs)** | 놓치면 의미 없음 |
| **둔감**(트랙 A 지식·트랙 C 아카이브) | **홈 섹션 + weekly digest** | 푸시할 만큼 급하지 않음 |

추가 가드:
- **야간 무음**(예: 21시~익일 8시 푸시 보류).
- **일일 푸시 캡**(하루 N건). 초과분은 묶음(digest)으로 강등.
- **묶기 우선**: 같은 날 여러 회수는 하나의 "모찌의 안부" 카드로 합친다.

## 5. 회수 카드 인터랙션 + 학습 루프

오발송("이미 샀는데?")이 신뢰의 최대 적이다. **모든 회수는 응답 가능**해야 하고, 응답이 lifecycle을 닫고 다음 타이밍을 학습한다.

```
[모찌의 안부]
"고민하시던 무선 마우스, 결정하셨어요?"
  ├─ 샀어요/끝냈어요 → instance archived, 다시 안 물음
  ├─ 아직요(나중에)  → 회수 주기 1회 연기(스누즈)
  └─ 그만 물어봐     → 이 항목 회수 영구 종료
```

- 채팅의 **proposal 카드 패턴을 그대로 재사용**한다(이미 confirm/cancel 흐름 있음 — `ProposalCardView.swift`). 능동 회수는 "모찌가 먼저 띄우는 proposal"인 셈.
- 응답은 다음 간격의 입력(트랙 A) 또는 영구 종료 신호. "그만"이 잦은 카테고리는 회수 자체를 줄인다. 콜드스타트는 기본값으로 시작해 점점 개인화.
- **단정 금지**: 항상 확인 질문 톤(*"샀나요"* ❌ → *"결정하셨어요?"* ⭕).

## 6. 홈 "모찌가 챙기는 것" 섹션

송준서 표현 — *"걱정 마세요, 모찌가 다시 알림 보내줄게요"*. **관리 패널이 아니라 안심 창**으로 설계한다(미션 §1.5 — 사용자가 정리하게 만들면 위반).

- 보여주는 것: 예정된 회수 목록(*"내일 약속 알려드릴게요"*, *"마우스 건은 다음 주에 다시 여쭤볼게요"*).
- 허용 액션: **가벼운 교정만** — 시간 미루기, "이건 됐어". 목록 정리·폴더링은 없음.
- 톤: 모찌가 *대신 기억해주고 있다*는 안도감. 할 일 목록(부담)이 아니라.
- **현재 홈 구조**: `HomeFeature.swift`의 3섹션(needsReview / analyzing / recent, TCA `@ObservableState`). 새 섹션은 여기에 state·action을 추가하는 형태.

## 7. 가드레일 (반드시)

- **민감 캡처 제외**: 비밀번호·금융 스크린샷이 회수 멘트에 노출되면 치명적. `PRIVACY_SENSITIVE_CAPTURE` 상 민감 플래그 항목은 능동 회수 대상에서 **원천 제외**. ⚠️ 단 현재 민감도 필드가 DB에 미구현 → MVP는 **channel allowlist**(공개 출처만 회수)로 임시 게이트, screenshot 등 회수 개방은 **sensitivity 필드 구현이 선결(blocker)**.
- **단정 금지**: 항상 확인 질문 톤(§5).
- **추출 실패 항목 회수 금지**: 빈 껍데기를 끈질기게 회수하면 스팸(§3 트랙 A-1).
- **학습 존중**: "그만 물어봐"는 영구 존중.

## 8. 기술 메모 — 어디에 얹나, 병목, 수평 확장

토론 중 송준서 질문("worker가 지금 뭐 하나, 병목 생기나, 수평 확장하면 pub/sub?")에 대한 코드 기반 답.

### 8-1. worker 현황 (`mochi_item_worker.py` + `main.py`)

- FastAPI와 **같은 프로세스** 안에서 `worker_concurrency`(기본 **2**)개 asyncio 태스크.
- 루프: `mochi_item_outbox`에서 `FOR UPDATE SKIP LOCKED`로 pending 1건 잠금(`in_flight`, `attempts+1`, `locked_until=180s`, item-level 직렬) → `AgentOrchestrator` 실행(LLM 멀티모달 분석 + 도구 + embedding + 프로필 요약 = **무겁다, 한 건 수 초~수십 초**) → 성공 `done`+분석완료 push / 실패 `pending`·`dead_letter`(5회).
- wake-up은 **5초 폴링**. `LISTEN mochi_item_outbox`는 코드 주석상 **TODO(미구현)**.

### 8-2. 능동 회수가 병목을 주나 → 어디에 얹느냐로 갈린다

| 방식 | 분석 throughput 영향 |
|---|---|
| 능동 회수를 **이 워커 루프에 합침** | ❌ 깎인다. 동시성이 2뿐이라 회수 스캔이 슬롯을 잡으면 *방금 캡처한 분석*(완료 푸시 대기 = 지연 민감)이 밀린다. |
| 능동 회수를 **별도 cron 트랙으로 분리** | ✅ 병목 0. 트리거 판정은 **SQL 조건**(D-1, 간격 도달, 결정 윈도우)이라 LLM 없이 가볍고, 발송은 APNs HTTP뿐. |

→ **분리한다.** 능동 회수는 본질이 지연에 둔감(1분 늦어도 무관), 분석은 지연에 민감. 같은 동시성 풀에 넣을 이유 없음. **Celery/APScheduler 신규 도입 불필요** — 기존 outbox 폴링 패턴을 시간축으로 확장한 가벼운 루프면 충분(Simplicity First).

### 8-3. 수평 확장 / pub/sub (송준서 직관 교정)

- **수평 확장 자체는 지금도 안전하다.** `FOR UPDATE SKIP LOCKED`가 바로 multi-process 경합용 패턴. 프로세스 N개 띄워도 같은 행 이중 처리 없음. **pub/sub가 확장의 *전제*는 아니다.**
- pub/sub로 가는 진짜 이유는 확장이 아니라 **지연·빈 폴링**이다(5초 지연 + 인스턴스 늘수록 빈 SELECT QPS ×N). `LISTEN/NOTIFY`나 Redis/SQS = 즉시 wake-up.
- 트레이드오프: Postgres SKIP LOCKED(현행) = 단순·트랜잭션 일관·exactly-once / 폴링 지연. vs 브로커 = 저지연·고처리량 / at-least-once라 멱등성을 직접 재구축(`attempts`·`locked_until` 장치를 브로커 쪽에).
- **능동 회수에 한정하면 pub/sub 거의 불필요** — "시간 도달 시 발송"이라 저지연 무의미, cron으로 충분. pub/sub의 가치는 *사용자 캡처 분석*(즉시성) 쪽이지 회수 쪽이 아니다.

### 8-4. 데이터 모델 스케치 (개념 수준 — 구현 아님)

두 종류 구분(materialize vs rule-eval):

- **고정 시각형(트랙 B)** → `scheduled_recall(owner, mochi_item_id, kind, fire_at, status, payload)` 테이블에 **미리 row 박음**.
- **조건형(트랙 A·C)** → 미리 박으면 stale(중간에 사용자가 보면 취소돼야 함). **워커가 주기적으로 SQL 재평가**해 그 시점 유효한 후보만 생성. 별도 테이블보다 규칙 스캐너.
- 홈 섹션(§6)은 둘을 합쳐 조회. 단 **채팅 로컬 reminder는 서버가 모르므로 홈에 안 뜸** — 합치려면 채팅 reminder의 서버 승격 필요(§9-2).
