# 트랙 C 능동 회수 — LLM 게이트 재설계 결정 (2026-06-17)

> 기존 `tech-plan.md` §8 의 트랙 C = "규칙 기반 ANN(cos≥0.6) → outbox 직행" 이 운영에서 난잡했다. 실데이터로 진단·실험해 **LLM 선별 게이트**로 방향을 바꾼 결정 기록. 구현 시 `tech-plan.md` §8 · `notification-agent.md` §3 을 이 결론에 맞춰 갱신해야 함(정합성 폭포).

## 1. 문제
트랙 C 가 저장할 때마다 무차별 발송(자기복제·자석앵커·완료알람·같은세션 메아리). 사용자 체감 "아직 안 까먹었는데 왜?" + "비교/묶기 권하는데 그 기능이 앱에 없음".

## 2. 방법 (실데이터, GCP DB 직접 조회)
- user1(개발자 본인, 124 item) + user2(OOS, 44 item) 의 item·intent·embedding·recall_outbox 를 export.
- **인과적(causal) 백테스트**: 각 item 저장 시점에 그때까지의 과거만으로 어떤 회수가 떴을지 재구성.
- LLM-judge 정성평가(이진 라벨 금지 — 정답 없는 문제, 라벨이 편향).
- 방식 비교 실험 E0~E3, 프롬프트 반복 v1~v5. (스크립트·개인데이터는 repo 밖 `/tmp/recall-analysis/`.)

## 3. 핵심 발견
1. **코사인 유사도는 회수 품질의 판별자가 아니다.** GOOD/BAD 코사인 범위 완전 중첩(최고점이 오히려 BAD). 임계값 상향은 정밀도 64% 천장 + GOOD 동반 손실 → **임계값은 레버가 아님.**
2. **규칙 필터 단독도 부족.** archived·근중복 제외만으론 발송률 99%→99%(자석앵커가 남음).
3. **LLM 선별 게이트가 레버.** top-N 후보를 LLM 이 보고 "다시 볼 가치 있는 1건"만 채택 → 발송률 99%→~35%, 자기복제·자석·완료·"같은 브랜드 다른 물건"을 정확히 거부. 미세 판별(조거팬츠↔조거팬츠 ⭕ vs 조거팬츠↔런닝화 ❌)은 임베딩·규칙으론 불가, LLM 만 가능.
4. **규칙은 LLM 에 거의 흡수됨(과적합 해소).** "필터→LLM"(E3) ≈ "LLM 단독"(E2). 정교한 규칙셋은 user1 8일에 과적합 위험만 — LLM 이 일반적으로 대체. 얇은 cheap 필터(archived·근중복·상태로그)는 비용/안전용으로만.
5. **OOS 일반화 확인.** user1 으로 만든 프롬프트를 user2 에 무튜닝 적용 → 발송률 ~22-32%, 채택분 전부 정상(노이즈 누수 0). N=2 라 방향성 증거(결론 아님), 단 과적합 의심은 반증.

## 4. 메시지(카피) 결정 — "아 맞다" 환기, 없는 기능 약속 금지
- 회수의 역할: ① 보는 순간 "아 맞다!" 기억 환기, ② 궁금하면 탭해서 확인. **"들어와서 액션해라"가 아님.**
- **금지**: 비교/묶기 등 앱에 없는 기능 약속(탭하면 단건 상세만 열림). `relation` enum "comparison" 이 카피에 "비교"로 새던 게 주범 → 내부 라벨임을 명시해 차단.
- **허용·권장**: 구체 명사 호명 + 현재 맥락에 얹기. 정당한 리마인더("…잊지 않으셨나요?")는 GOOD(v2 가 과교정으로 죽였던 것 복구).
- **프롬프트는 criteria, not examples** (skill-creator 철학): 구체 예문을 넣으면 거기 과적합(v3 가 "…고려하고 계신가요?"로 54% 수렴). v4/v5 에서 예문 제거 + anti-template 지시 → 어미종류 13→34, 최빈 54%→22%, 평균 63→49자.
- **확정 프롬프트 = v6(영어 system prompt, 한국어 출력).** v5 + 실출력 검증 보강(§10) — 메시지 내면 단정 금지·셀렉션 상태스냅샷 거부를 *케이스 박지 않고* 일반 원칙으로. 영어로 작성(기존 트랙 A/B `recall_planner_prompt.py` 와 컨벤션 일치). 전문·구현은 §7.

## 5. 확정 아키텍처
```
임베딩 ANN(overfetch ~30~50) → 앱단 얇은 필터(archived·근중복 cos≥0.92·상태로그) → top10
  → LLM 선별 게이트(v6 프롬프트, gemini-3.1-flash-lite, 0~1건 채택+한국어 작문)
  → 결정적 백스톱(트리거 디바운스·하루 cap·owner 쿨다운; 동시성 레이스/비결정성 방어)
  → notification_outbox(kind=recall) → 기존 발송·landing 재사용
  + 명시 피드백 수집(응답카드/dismiss) ← 검증 루프(필수)
```
- LLM 게이트 = 기존 `GeminiRecallPlanner` 패턴 재사용(트랙 A/B 와 동형). 인프라 신규 없음.
- **cap/dedup 은 규칙으로**(LLM·window-context 에 맡기지 않음): flash-lite 비결정성 + worker 동시성(=2) 레이스로 샘. window-context 는 LLM 의 *소프트* 판단 보강용만.
- 필터는 SQL 조인 말고 **앱 코드에서**(앵커 MochiItem 어차피 로드). 현 스케일(유저당 수백 벡터)은 exact KNN 이라 인덱스 문제 없음 — overfetch→filter→topN 은 scale-ready 패턴.

## 6. 정직한 한계 (반드시 인지)
- **만족도 지표 부재.** 클릭율 ≠ 만족(알림 보고 "아맞다"만 해도 미션 달성, 안 눌러도 됨). 백테스트=in-sample, CTR=clickbait 편향 → **둘 다 못 씀.** 유일한 출구 = 명시 피드백(응답카드/dismiss). 이거 없이 프롬프트 더 죄는 건 깜깜이.
- **N=2, 둘 다 밀집 dev-ish 데이터.** user2 는 노이즈 적은 "깨끗한" 유저라 rejection stress-test 는 user1 에서만 강함.
- **v5 잔여**: "비교" 2건 누수 = 상태로그(홈화면 구성·시세 기록)가 앵커로 뽑힌 케이스. 메시지가 아니라 **셀렉션에서 상태로그 거부 강화**로 해결.

## 7. 확정 프롬프트(v6) — 구현 이관 완료 (`recall_gate_prompt.py`)
영어 system prompt, 한국어 메시지 출력. 실코드 출력은 `submitRecallDecision` tool-call(`gemini_recall_gate.py`), 실험 스크립트는 JSON 계약 `{recall,chosen_index,relation,confidence,message,reason}`. v5→v6 변경은 §10. 골자:
- recall 정의(탭=단건 상세만, 두 역할 a/b) → 없는 기능 약속 금지 + relation 누수 트랩
- 선택/거부 기준(같은 결정·재료·미해결 thread / 재저장·일회성·같은브랜드다른물건·상태로그 거부)
- 메시지: 템플릿 금지·anti-template, 구체명사 호명, 명령/장황 금지, 리마인더 허용, 단정 금지

## 8. 구현 (완료 2026-06-17)
- **구현됨**: 신규 `infrastructure/gemini_recall_gate.py`(genai 어댑터, planner 패턴 재사용)·`recall_gate_prompt.py`(v5 영어, 한국어 출력)·`domain/recall_gate.py`(포트+입출력). `generate_recall_candidates.py` 재작성(overfetch→필터→게이트→백스톱). `recall_candidate_repository.py` +`recent_owner_recall_exists`/`acquire_owner_lock`(발송 워커와 동일 advisory key). `config.py` 게이트 키. `recall_planning_factory.py` 배선. 단위테스트 10건.
- **결정(architect 플랜)**: 트리거 디바운스=owner 쿨다운(스키마 무변경) / `recall_gate_enabled=false`=결정적 best-1 폴백(롤백 안전판) / temperature=0.2(v5 재현). DOMAIN_DESIGN 폭포 없음(스키마 무변경), openapi 무관(피드백 경로 기존 완비).

- **운영 단계**: 2026-06-17 prod(`mochi-svc`) 배포 + **실발송 전환 완료** — `recall.conf`(systemd drop-in) `RECALL_GATE_DRY_RUN=false`(발송측 `RECALL_NOTIFICATIONS_DRY_RUN` 이미 false, 야간침묵 24~0 off). 도그푸딩으로 v6 멘트 품질·발송률·상태로그 누수(§6) 를 게이트 로그(`recall.gate.decision`)로 관찰하며 다듬는 중. 되돌리려면 `RECALL_GATE_DRY_RUN=true` 또는 `recall_gate_enabled=false`(결정적 best-1 폴백). ⚠️ `recall.conf` 는 `docs/INFRA.md` 미문서화(재배포 재현성 위해 추가 필요).

## 9. 실험 결과 상세 + 실제 응답 예시

> flash-lite(temperature 0.2) 비결정성으로 실행마다 ±1~2건 변동. 추세는 견고.

### 9.1 방식 비교 (user1, 120 트리거, 인과 백테스트)
| 방식 | 발송 | 결론 |
| --- | --- | --- |
| E0 현행: max-cos top1, cos≥0.6 | 120/121 (99%) | 저장마다 발송 = 게이트 무의미 |
| E1 규칙필터만: archived·근중복 제외 | 120/121 (99%) | 자석앵커가 남아 무효 — **규칙 단독 실패** |
| E2 LLM만: top8 raw → LLM 선별 | 44/121 (36%) | LLM 이 자기복제·자석·완료 알아서 거부 |
| E3 필터→LLM: top8 필터후 → LLM | 43/121 (35%) | **E2≈E3 → 규칙이 LLM 에 흡수(과적합 우려 해소)** |

### 9.2 프롬프트 반복 (E3 고정, train=user1 / OOS=user2 무튜닝)
| ver | 변경 | u1 발송 | u1 "비교/묶" 누수 | u1 어미종류/최빈% | u1 평균길이 | u2(OOS) 발송 | u2 누수 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| v2 | criteria 시도(예시 잔존) | 45 (37%) | **51%** | — | — | 8 (21%) | **87%** |
| v3 | 없는기능 약속금지 + relation 누수 트랩 | 53 (43%) | **0** | 13종 / 54% | 63자 | 12 (32%) | 0 |

### 9.3 실제 응답 BEFORE(v2) → AFTER(v5) — 없는 기능 약속 제거
- **마제소바 레시피 영상**
  - v2: 지난번에 저장하신 일본식 라면집 '카키 코우죠', 이번 마제소바 레시피와 함께 **비교해보시겠어요?**
  - v5: 카키 코우죠에서 먹었던 일본식 라면 맛이 생각나서 마제소바 레시피도 찾아보셨나요?
- **유니클로 추천 아이템(셔츠·와이드진)**
  - v2: …'너드킹 추천 패션 제품 리스트'와 이번 유니클로 아이템을 함께 **비교해 볼까요?**
  - v5: 며칠 전 저장해둔 너드킹의 패션 제품 리스트도 함께 살펴보면 좋겠네요.
- **월드컵 육즙타코 레시피**
  - v2: …정재형 마제소바 레시피와 함께 이번 주말 요리 **리스트로 묶어볼까요?**
  - v5: 따라쿡에서 봤던 정재형 마제소바 레시피도 이번 주말 요리 리스트에 함께 올려두셨나요?
- **월치 캡슐세제 광고**
  - v2: …위칙 소독 섬유유연제와 함께, 이번 월치 캡슐세제도 세탁 용품으로 **비교해볼까요?**
  - v5: 위칙 섬유유연제 보실 때 함께 고려했던 월치 캡슐세제도 생각나네요.
- **무신사 헨리넥 티셔츠**
  - v2: …지난번 고민했던 마인드브릿지 와플 헨리넥도 다시 **비교해 볼까요?**
  - v5: 얼마 전 봐두었던 마인드브릿지 와플 헨리넥 티셔츠도 함께 고민 중이셨죠.
- **아이스트 PDRN 크림**
  - v2: …아누아 PDRN 미스트와 이번 쥬비렉스 PDRN 크림, 성분별로 **비교해 볼까요?**
  - v5: 아까 저장해두신 아누아 PDRN 미스트도 피부 탄력 관리용으로 보셨던 것 기억나시나요?

## 10. v6 보강 — 실출력으로 메시지·셀렉션 일반 원칙화 (2026-06-17)

> v5 가 "확정"이었으나 §9.3 의 v5 실제 멘트를 사용자와 다시 보니 미션과 어긋나는 패턴이 드러나 v6 으로 보강. 핵심 = **모델에 케이스를 박지 않고(overfit 금지) 일반 원칙 둘로** 잡음. 실험 산출물: `/tmp/recall-analysis/sys_prompt_lean_en.txt`(=v6 본문), `verify_lean40.py`.

### 10.1 진단 — v5 메시지의 공통 결함 = 사용자 내면 단정
v5 가 사용자의 속마음·동기·인과를 안다는 듯 단정 → 환기 대상(사용자가 *남긴 기록*) 대신 모찌가 *지어낸 서사*를 들이밂. 서사가 어긋나면 "아 맞다"가 "어? 난 안 그랬는데"로 뒤집혀 회수 실패:
- "…마제소바 레시피도 찾아보셨나요?"(맛이 생각나서) = 저장 **동기** 창작
- "…함께 고민 중이셨죠." = **심리상태** 단정
- "…함께 고려했던 월치 캡슐세제" = 두 기록을 한 시점에 묶은 **인과** 단정

v5 의 "Never state as fact an action(bought/visited/finished)" 는 *물리 행위*만 막아 내면·동기·인과는 다 샜음.

### 10.2 overfit 경로 폐기 (skill-creator)
검증 실패 케이스를 보고 한국어 표지("~ 보실 때 함께", "~ 생각나서 …하셨나요")·구체 예시("식당 vs 레시피")를 프롬프트에 박는 건 **v3 가 한 패턴 54% 수렴한 함정의 재현**(모델이 그 표지만 피하고 다른 형태로 같은 잘못). skill-creator "Improving the skill": generalize-don't-overfit / keep lean / explain why / NEVER 남발=yellow flag. → 케이스 빼고 일반 원칙 둘.

### 10.3 v6 두 원칙 (criteria + why, 예문 없음)
1. **메시지**: 모찌가 아는 사실은 "이 기록이 존재하고 사용자가 저장했다" 뿐 — 왜·무슨 생각·무엇과 연결했는지는 모른다. 기록에서 말하되 상상한 이야기로 말하지 마라(동기·심리·미목격 행위·공유 순간 금지). 빗나가면 "아 맞다"→"어, 그런 적 없는데".
2. **셀렉션**: 표면 토픽 말고 그 기록이 사용자에게 *실제로 무엇인지*로 타겟 판단(같은 토픽도 다른 결정이면 거부) + 사용자가 그냥 기록해둔 *시점 상태 스냅샷*(돌아갈 열린 질문 없음)은 거부.
