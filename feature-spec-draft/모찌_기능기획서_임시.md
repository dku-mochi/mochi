## 1. 제품 한 줄 정의 · 미션

> 모찌는 스크린샷·링크·텍스트 메모를 AI 가 자동으로 분석해 **일정·할 일·지식·기록**으로 분류하고 다시 찾아주는 iOS 멀티모달 기록 관리 에이전트다.

**미션 — 모든 기능 결정의 기준:**

> **놓치기 쉬운 순간은 쉽게 남기고, 필요한 기억은 쉽게 떠오른다.**

- **입력은 더 쉽게, 분류와 회수는 AI 가.**
- "떠올린다(사용자가)" 가 아니라 **"떠오른다(모찌가 알아서)"** — 회수의 능동 주체는 모찌다.
- **기본 회수 경로는 모찌가 먼저 띄운다**: 홈의 중요 제안, 질문 탭의 능동 답변, 일정·할 일 알림.
- **검색 탭과 분류 수정(Intent 변경)·삭제는 control/fallback surface 다** — 사용자가 직접 찾아야만 하는 유일한 길로 두지 않는다. 검색은 "모찌가 못 떠올렸을 때의 안전망"이지 기본 동선이 아니다. (근거: `PRODUCT.md §1.5, §13`)

## 3. 글로벌·횡단(Cross-cutting) 기능

### 3.1 4-Intent 자동 분류 (1:N, 위계 없음)

모든 입력(MochiItem) 1건은 AI 가 4가지 Intent 중 1개 이상으로 분류한다. **입력 1건 = MochiItem 1개** (쪼개지 않는다).

| Intent | 표시명 | 정의 | 예시 | 컬러/아이콘 |
|---|---|---|---|---|
| `schedule` | 일정 | 특정 시간에 발생하는 이벤트 | 내일 3시 팀 회의 | Lavender / calendar |
| `todo` | 할 일 | 완료 여부가 중요한 작업 | 보고서 제출하기 | Peach / check |
| `knowledge` | 지식 | 다시 학습·참고할 정보 | RAG 구조 설명 글 | Mint / book |
| `memo` | 기록 | 맥락 보존이 중요한 메모 | 회의 내용·감상·일상 | Sky / document |

**모델 (근거: `DOMAIN_DESIGN.md §4.4` flat `intents` 타겟 · `INTENT_REDESIGN.md`)**
- **1:N · 위계 없음:** 한 MochiItem 은 여러 의도를 **동등하게** 가진다. `intents = [{intent, applicability, label?, reasoning?}]` flat 리스트가 원천. **primary/secondary 위계는 폐기 방향** — UI 의 "대표 칩"은 저장 위계가 아니라 `argmax(applicability)` 로 계산되는 **projection** 일 뿐이다.
- **applicability:** 각 의도의 적용 강도 0~1. `confidence = max(applicability)` (저장하지 않고 계산).
- **active intents:** `applicability ≥ τ` 인 의도 **집합**. 비면 **`memo` 로 fallback** (분류 실패해도 잃지 않는다 → 미션 정합).
- **"헷갈려요"(needs_review):** `confidence < τ_review` 일 때 사용자에게 분류 확인 요청(§P-02). `τ_review` 는 **실험으로 확정 전(config 상수)**. 현재 iOS 는 임시로 `confidence < 0.6` 을 client-derive 로 판정하며, 이 0.6 은 제품 임계값이 아니다.
- **3상태:** 헷갈림(최상위도 약함) / 단일 확신(top1≥τ, top2<τ) / 복수 의도(top1·top2 둘 다 ≥τ → 둘 다 적용, 헷갈림 아님). (근거: `DOMAIN_DESIGN.md` 부록 C)

### 3.2 4-Intent 생명주기(Lifecycle)

레코드 lifecycle 은 intent 와 **독립**(record 단위)이다. (근거: `DOMAIN_DESIGN.md §7`, 코드 `lifecycle_policy.py` 정본)

```
ingested → analyzing → active → archived
   │           │          (knowledge 만) ↘ decaying → reviewRequested → (active | archived)
   └────┬──────┘
        ▼
      failed  → archived(userManual)
```

> ⚠️ **`failed` 는 `ingested`/`analyzing` 단계에서만 진입**한다. `active → failed` 전이는 **없다**. `failed` 에서 나갈 수 있는 곳은 `archived(userManual)` 뿐. (정본 `_ALLOWED_KIND_PAIRS`, 아래는 요약)

| Intent | 자동 동작 | 합법 전이 (요약) |
|---|---|---|
| 일정 | 종료 후 자동 기록화 · 캘린더 sync | `ingested→analyzing→active→archived(scheduleEnded \| userManual)` |
| 할 일 | 완료 시 archived · 미완료는 홈 제안 · Reminders sync | `ingested→analyzing→active→archived(todoCompleted \| userManual)` |
| 지식 | 30일 미회수→decaying, 180일 후→reviewRequested · RAG 인덱싱 | `ingested→analyzing→active→decaying→reviewRequested→(active 복귀 \| archived(knowledgeStale \| userManual))` |
| 기록 | 영구 보관 | `ingested→analyzing→active→archived(userManual)` |

> **공통 예외 전이:** 모든 Intent 는 `ingested`/`analyzing` 단계에서 `failed` 로 빠질 수 있고, `failed→archived(userManual)` 만 허용. 위 표의 intent별 전이는 정상(happy) 경로 요약이다.

**자동 전이 (worker 주기 실행, 근거 `DOMAIN_DESIGN.md §7.4`)**
- `schedule ∈ active` & 종료시각 경과 → `archived(scheduleEnded)`
- `todo ∈ active` & 완료 → `archived(todoCompleted)`
- `knowledge ∈ active` & 마지막 회수 후 **30일** 경과 → `decaying`
- `decaying` 진입 후 **180일** 경과 → `reviewRequested`
- dead-letter(outbox `attempts > max`) → `failed`

### 3.3 입력 채널 (3+1 통일 경로) + 멱등성

저장 마찰 최소화가 미션의 절반.

| 채널 | 표면 | channel 값 | 설명 |
|---|---|---|---|
| 백탭 (Back Tap) | C-01/C-02 | `screenshot` / `appDirectInput` | 뒷면 2~3회 탭 → 단축어 → snippet 카드 → 캡쳐/메모 |
| 공유시트 (Share Sheet) | E-01 | `screenshot`/`safari`/`appShareSheet` | 외부 앱 공유 → 이미지/텍스트/링크 수신 (host·hasImage 기반 guessChannel) |
| 앱 내 빠른 입력 | C-03 | `appDirectInput` | 홈 우측 상단 작은 입력 버튼 |
| Siri / Spotlight | E-02 | `appIntent` | 음성·검색으로 텍스트 메모 직접 적재 (보조) |

**멱등성(필수 불변식, 근거 `ARCHITECTURE.md §3.4·§4.1`, `DOMAIN_DESIGN.md §8.1`)**
- `POST /mochi_items*` 를 발생시키는 **모든 ingest 흐름**(백탭 캡쳐·메모, 공유시트, 앱 직접 입력, 동기화 재시도)은 **owner-scoped `Idempotency-Key`** 를 생성·전송한다.
- 같은 키 재요청 → 서버는 **기존 MochiItem 을 그대로 반환**(중복 생성 금지). iOS `MochiItem.id`(로컬 PK)를 멱등키 원천으로 쓴다.

### 3.4 이미지 업로드 · 저장 계약 (원본 로컬 우선)

(근거: `ARCHITECTURE.md §3.4`, `DOMAIN_DESIGN.md §5·§9`, `PRIVACY_SENSITIVE_CAPTURE.md §1.1`)

- **원본은 기본 로컬:** 원본 PNG/HEIC 는 iPhone App Group(`captures/`)에 보관. 서버로는 원본을 자동 전송하지 않는다.
- **업로드용 파생:** 서버 분석이 필요하면 원본 → **JPEG(긴 변 ≤1920px, q60)** 파생 → `sha256/mimeType/byteSize` 산출.
- **Signed URL 직업로드:** `POST /mochi_items/presign` → V4 Signed PUT URL → 클라이언트가 **GCS 에 직접 PUT** → `objectKey` 만 ingest 에 전달(이미지 bytes 는 API 본문에 싣지 않음).
- **IDOR 방지(보안 불변식):** storage prefix `captures/{owner_id}/...` 강제. presign·ingest 진입점에서 owner-prefix 를 검증해 타인 objectKey 주입을 차단.

### 3.5 민감 캡처 보호 (Privacy)

스크린샷·텍스트에 의도치 않은 민감정보가 섞일 수 있으므로, **기기에서 먼저 감지**하고 위험도에 따라 처리한다. (근거: `PRIVACY_SENSITIVE_CAPTURE.md` 전체)

| 점수 | 등급 | 기본 동작 |
|---:|---|---|
| 0–2 | 낮음(low) | 일반 업로드 가능 |
| 3–5 | 주의(caution) | 텍스트/메타데이터 중심 업로드 |
| 6–8 | 민감(sensitive) | 사용자 경고 + 원본 업로드 차단 기본값 |
| 9–10 | 매우 민감(highly_sensitive) | 로컬 저장 기본값, 명시 승인 없이는 서버 분석 금지 |

- **온디바이스 감지:** Vision OCR · VisionKit/Live Text · NSDataDetector · NaturalLanguage NER + 한국형 룰(주민번호·카드 Luhn·계좌·OTP·토큰·의료·금융 등) + 조합 가중치 → 0~10 점(10 cap).
- **원본 비공개, 의미 보존:** 카드번호 전체 대신 `[카드: 신한카드 끝자리 3456]` 처럼 구조화 의미 표현만 서버 전송.
- **서버 전송 payload 필드(필수):** `sensitivity_score:int` · `sensitivity_level:(low|caution|sensitive|highly_sensitive)` · `redaction_status:(none|detected|masked|semantic_replaced|user_approved_original)` · `original_image_uploaded:bool` · `privacy_policy:(local_only|text_only|redacted_image|original_allowed)` · `redactions:[{type, replacement, risk}]`.
- **Agent fallback(서버):** ① 원본 없음 → semantic payload + OCR 텍스트로 분석 ② redacted 이미지 있음 → redacted + payload 함께 ③ 원본 승인 → 임시 이미지 사용 후 **TTL 삭제**.
- **백탭 캡쳐 분기 연동(§7.1 연동 지점):** 백탭 캡쳐는 background OCR 비용 문제로 즉시 감지가 어렵다 → **로컬 `pendingUpload` 보존 후 다음 앱 active 시 CorePrivacy 감지** → 점수 6↑ 면 **업로드 보류 + P-01 표시** → 사용자 선택 후에만 sync. (점수 미산출 상태로 서버 ingest 로 직행하지 않는다.)
- 사용자 선택지: 기기에만 저장 / 민감 영역 가리고 분석 / 텍스트만 분석 / 원본 분석 허용(매번 명시 승인).

### 3.6 AI 회수 · 분석 (검색 · 질문 · 그라운딩)

- **Hybrid Search:** BM25(tsvector GIN) + 벡터(HNSW 768d) → RRF(k=60) 융합 → (옵션) Rerank → answer + citations. **모든 검색은 `owner_id` 필터 강제.**
- **자연어 질문(RAG):** Query 분석 → Hybrid Search → Tool 호출 → 답변 + **근거 모찌 표시(환각 방지 필수)**.
- **URL 그라운딩 도구:** `PlatformContextTool` 이 YouTube(oEmbed+watch metadata)/X(`publish.x.com/oembed`)/Instagram(Meta oEmbed 또는 OG fallback, 이미지 의존 높아 screenshot Vision 을 primary context)을 우선 처리, 그 외 일반 URL 은 `WebFetchTool`.
- **WebFetch SSRF 가드(보안 불변식):** 호스트 블록리스트 + 모든 A/AAAA 응답 IP 검증(DNS rebinding 방어) + **매 redirect hop 재검증** + private/link-local/metadata/multicast IP 차단 + 스트리밍 byte limit + MIME 화이트리스트. (근거 `ARCHITECTURE.md §3.5`)
- **상대 날짜 기준시각:** Agent 분석 입력에 매 run `Asia/Seoul` 현재시각을 주입. "내일/다음 주 금요일/마감" 해석은 이 기준을 따른다. (근거 `ARCHITECTURE.md §5.4`)
- **개인화 프로필:** `user_profiles` 에 **raw 내용이 아니라** "관심사·평소 분류 성향" 추상 요약만 sliding-window 로 적립(owner-scoped, cross-tenant 차단). 분석 시 system prompt 에 주입 → 쓸수록 정확. AI 데이터 안내(§G-01)에 포함.

| 구성 | 모찌 캐릭터 · **Apple 로그인** · **Google 로그인** · 약관/개인정보 링크 |
| 기능 | ① Apple 로그인(프라이버시 친화) ② Google Sign-In ③ OAuth 성공 → `POST /auth/{apple\|google}` → **JWT(RS256) + refresh token rotation** 발급 ④ 신규/기존 분기 |
| 예외 | OAuth 취소/네트워크 실패 → 에러 안내 + 재시도. refresh `reuse_detected` → family 폐기·재로그인 |

### S-03. 회원가입 (OAuth 신규 생성 + 약관 동의)

> 모찌는 별도 이메일·비밀번호 회원가입 폼이 **없다.** OAuth 첫 성공 = 회원 생성. 단, 약관 동의·최초 프로필을 거친다.

| 구분 | 내용 |
|---|---|
| 트리거 | 신규 provider/subject 인증 성공 |
| 기능 | ① 서버가 `users` 행 자동 생성(email·display_name·locale `ko-KR`) ② `auth_accounts` 에 provider·subject 연결 ③ 서비스 약관 + 개인정보 처리방침 동의 ④ **AI 분석에 사용되는 데이터 안내(개인화 프로필 요약 포함)** ⑤ 온보딩 이동 |
| 사후조건 | 신규 user 식별, refresh token family 발급, `onboarding_completed_at = null` |
| 예외 | 약관 미동의 → 진행 불가. 이미 연결된 provider/subject → 기존 계정 로그인 |

### I-01. Inbox (분석 대기·진행)  — sync 실패 ≠ 분석 실패 분리

| 상태 | 표시 | 재시도 정책 |
|---|---|---|
| 업로드 대기/진행 | "올리는 중"(`pendingUpload`) | — |
| **업로드 실패(`syncFailed`)** | "보내기 실패" | `pendingUpload` **1회 retry 후 `syncFailed` marking, 자동 재시도 없음** → 사용자 "다시 보내기" 필요 |
| 분석 진행 중 | "모찌가 정리하는 중" | `GET /mochi_items/{serverID}` **3초 폴링**, `active` 시 반영 |
| **분석 실패/지연(lifecycle `failed` 또는 90s 초과)** | "정리 못 함" | `demoteToManual` → "헷갈려요(의견 없음)" + 직접 분류 + **"다시 맡기기"(`requeueForAnalysis`)** |

> 두 실패는 원인·정책이 다르다: `syncFailed` = 업로드(네트워크) 실패, lifecycle `failed` = outbox dead-letter(분석) 실패. (근거 `DOMAIN_DESIGN.md` 부록 D, `ARCHITECTURE.md §2.3·§3.4`)

| 보안 — 인가 | **모든 repository read/write/search/export/delete 는 `owner_id` 필터 강제**(누락 시 P1). DB FK 아닌 app-level 격리 |
| 보안 — 멱등성 | `POST /mochi_items*` 에 owner-scoped `Idempotency-Key` 필수 |
| 보안 — SSRF | WebFetch: 호스트 블록리스트 + A/AAAA IP 검증 + redirect 재검증 + private/metadata/multicast 차단 + MIME allowlist + byte limit |
| 보안 — Storage | `captures/{owner_id}/` prefix + V4 Signed PUT + owner-prefix 검증(IDOR 방지) |
| 보안 — 에러 | 통일 envelope `{code, message, requestId, retryAfter}` · `X-Mochi-Request-ID` echo·로그 연결 |
| 개인정보 | 원본 삭제 · 분석 결과 수정 · 데이터 내보내기 · 계정 삭제(soft delete, email 익명화 TODO) · AI 사용 데이터 고지(개인화 프로필 owner-scoped 요약) |
| 접근성 | Dynamic Type · VoiceOver label(아이콘 포함) · 색상만으로 Intent 구분 금지 · 충분한 대비 |

## 12. 구현·계약 상태 매트릭스 (제품 요구 ≠ 현재 계약)

> 이 문서는 **제품 요구**를 적는다. 아래는 정본(`DOMAIN_DESIGN.md §6`, `ARCHITECTURE.md §4.2`)이 명시한 **현재 서버 계약 상태**다. 혼동 방지를 위해 분리한다.
