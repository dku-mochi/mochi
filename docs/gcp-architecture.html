01 — Assumptions

트래픽 가정에서 출발

이 트래픽 수치는 모든 의사결정의 출발점이다. 모찌의 MVP 는 콘테스트 시연 + 초기 베타 단계로, 사실상 idle 시스템.

유저

DAU 100

  • MAU 500 가정
  • 피크 동시 사용자 ~ 20명
캡쳐

2건/유저/일

  • 200건/일 = 6,000/월
  • 평균 RPS 0.002, 피크 0.05
  • 이미지 평균 500 KB
대화

2건/유저/일

  • 200건/일 = 6,000/월
  • 동시 SSE 연결 피크 ~5
  • 평균 응답 시간 5~10s
철학 — 이 트래픽에서 over-engineering 의 위험

DAU 100 은 1 vCPU instance 하나가 95% 시간 idle 인 상태다. 이 위에 LB + Armor + NAT + VPC Connector + Redis + 4개 service 분리를 얹는 건 비용보다도 운영 복잡도 가 더 큰 문제다. 콘테스트 1주일 전 인프라 장애 디버깅 시간이 늘어남. 그래서 이번 MVP 는 "빠질 수 있는 건 다 뺀다" 원칙으로 재설계한다. 확장은 임계 (DAU 500+, p95 SLO 위반) 가 측정될 때.

결정 · API · SSE · Worker 를 한 process 안에

이전 안의 4-service 분리는 DAU 100 에서 over-engineering. FastAPI startup 이벤트에 asyncio.create_task(outbox_poller()) 하나 띄우면 같은 process 가 (1) HTTP 요청, (2) SSE 연결, (3) background outbox poll 을 모두 처리. 안전성: instance 가 scale up (1→2→3) 되어도 outbox 의 FOR UPDATE SKIP LOCKED 가 중복 픽업 막음 — 멀티-instance race 안전이 이미 schema 수준에 보장됨. 운영성: 코드 한 곳, 배포 한 번, 로그 한 stream.

04 — Flows

핵심 데이터 흐름

서비스가 단순해진 만큼 데이터 흐름도 단순. 같은 process 안에서 ingest → outbox → worker → SSE push 가 모두 일어난다.

4.1 Capture ingestion (POST /captures)

5번 응답 후, 같은 instance 의 background outbox poller 가 다음 polling cycle (기본 1초) 에 새 row 를 lease 해 처리한다.

4.2 Outbox worker (background task)

# FastAPI startup
@app.on_event("startup")
async def start_outbox_poller():
    asyncio.create_task(outbox_poller_loop())

async def outbox_poller_loop():
    while True:
        try:
            async with db_session() as s:
                rows = await pick_outbox_lease(s, lease_owner=POD_ID, lease_ms=60_000, limit=4)
            for row in rows:
                await process_capture(row)        # Gemini 호출 + 임베딩 + derived row
        except Exception as e:
            log.error("outbox_poller_error", exc_info=e)
        await asyncio.sleep(1.0)
  • Cloud Run instance 가 scale up 으로 2-3개가 되어도 FOR UPDATE SKIP LOCKED 가 race 안전 보장
  • instance 가 죽으면 locked_until 만료 후 다른 instance 의 poller 가 자동 reclaim
  • polling 1s × DAU 100 트래픽 = DB 부하 무시 가능 (single user 시야)

4.3 SSE 스트리밍

iOS 가 GET /captures/{id}/stream 으로 연결 → 같은 instance 의 SSE 핸들러가 agent_runs.current_node 를 1초 간격 폴링 → 변경 시 client 로 push. 멀티-instance 가 되어도 worker 와 SSE 가 다른 instance 에 있을 수 있는데, DB 가 진실의 원천이라 polling 이 정상 동작 (Redis pub/sub 같은 fan-out 불필요).

4.4 Hybrid search

POST /search → 같은 process 안에서 (1) Vertex AI embed query (~30-100ms, Tokyo 라 빠름), (2) BM25 + 벡터 두 쿼리 병렬, (3) RRF k=60 결합, (4) Gemini synthesizer 로 answer 생성, (5) citations 와 함께 반환. 모든 단계가 같은 한 process 안.

06 — Security

보안 — 핵심만 남기기

정교한 perimeter (VPC SC · Armor · NAT 고정 IP) 는 운영기 이슈. MVP 는 application + IAM 레벨에서 정확하게 막는다.

인증 (Authentication)

  • iOS 가 Apple/Google ID token 획득 → POST /auth/{provider}
  • 서버가 Apple/Google JWKS 로 검증 (in-process TTL cache)
  • 자체 JWT (RS256) 발급 — Cloud KMS 가 서명 위임, private key 미노출
  • access token 30분, refresh token 30일 (rotating)

인가 (Authorization)

  • repository 레이어가 keyword-only owner_id 강제 — cross-tenant 누설 컴파일 시점 차단
  • presigned URL 발급 시 users/{user_id}/ prefix 검증
  • Cloud SQL: Cloud Run SA 의 cloudsql.client IAM 만 허용
  • GCS: uniform IAM + public prevention=enforced

네트워크

  • Cloud SQL public IP 켜되 Authorized Networks 0개 — 외부 접근 차단
  • Cloud Run 의 --add-cloudsql-instances 가 내부 Unix socket 자동 mount (TLS + IAM)
  • Vertex AI 는 public endpoint + service account 인증 (PSC 미사용)
  • Cloud Run 의 기본 ingress 가 DDoS basic 보호 + TLS

App-level (기존 backend 유지)

  • Idempotency-Key — owner-scoped SHA-256, TTL 30일
  • WebFetchTool — 사설/링크로컬/메타데이터/multicast IP 차단, redirect hop 별 재검증, MIME 화이트리스트, byte limit
  • Pydantic 입력 검증, DTO 레벨 길이·타입·enum 강제
  • Rate limit — 앱 레벨 token bucket (in-process, per user)
Trade-off · MVP 가 받는 위험과 그 의식적 수용

(a) Cloud Armor 없음 → L7 DDoS 시 Cloud Run 이 max=3 까지 scale 후 throttle. 콘테스트 데모 단계엔 noise 미미. (b) Cloud NAT 없음 → WebFetchTool outbound IP 가 가변. 일부 사이트가 차단할 수 있음 — 실측 후 대응. (c) VPC SC 없음 → service account 키 유출 시 데이터 exfil 가능 — Workload Identity 강제, key 발급 자체를 안 함. (d) CMEK 미적용 (GCS · SQL) → 기본 Google-managed encryption-at-rest. compliance 요구 들어오면 toggle 만으로 on.

07 — Trade-offs

결정 매트릭스

모든 의미 있는 결정과 그 대안. 선택 채택, 기각 미채택, 보류 → 미결정.

결정 #1 · 컴퓨트 = Cloud Run service 1개로 통합

대안: API · SSE · Worker · Housekeeper 4개 분리 (이전 안). 이유: DAU 100 트래픽에선 instance 가 거의 idle. 분리하면 idle 비용 × 4. 같은 process 안에서 asyncio background task 로 worker 띄우는 게 표준. 대가: instance burst 시 worker 도 같이 늘어남 (idle worker capacity 낭비 가능) — DAU 100 에서 무시 가능. 전환 임계: 동시 SSE 100+, 또는 worker 처리 시간이 request CPU 와 충돌하기 시작할 때.

결정 #2 · DB = Cloud SQL db-g1-small (shared CPU)

대안: db-custom-1-3840 ($50/월, 안전), AlloyDB ($300+/월). 이유: HNSW 메모리 6K caps × 5 chunks × 768 × 4B = 92 MB raw, 1.5x overhead = 140 MB. 1.7 GiB 인스턴스에서 30 GiB pglogical buffer 까지 여유. 대가: shared CPU 라 burst 성능 제한. 5명 동시 search 시 latency 튈 수 있음. 전환 임계: DAU 300, 또는 search p95 > 1.5s 측정 시 db-custom-1-3840 으로.

결정 #3 · Cloud SQL = public IP + Cloud Run native socket

대안: private IP + Serverless VPC Connector. 이유: Cloud Run 의 --add-cloudsql-instances 가 IAM 기반 + TLS Unix socket — public IP 라도 외부 접근 차단 + 내부 통신은 private 와 동일 보안. VPC Connector $16/월 + 운영 부담 절약. 대가: Memorystore Redis 같은 다른 private VPC resource 가 필요해지면 VPC Connector 도 같이 들어와야 함.

결정 #4 · 외부 진입 = Cloud Run domain mapping (LB 미사용)

대안: External HTTPS LB + Cloud Armor. 이유: Cloud Run 의 domain mapping 은 무료, managed TLS 자동, HTTP/2 + HTTP/3 모두 지원. LB 의 $20/월 + Armor $6/월 + 운영 복잡도 절약. 대가: rolling deploy 시 traffic split 은 Cloud Run revision-level 기능으로 대체. URL map 기반 path routing 안 됨 (불필요).

결정 #5 · 메시징 = DB Outbox (기존 결정 유지)

대안: Pub/Sub topic + push subscription. 이유: capture INSERT 와 enqueue 가 같은 트랜잭션 안에 있어야 일관성 보장. outbox 패턴이 retry / DLQ / lease 까지 한 테이블에서 통일. 대가: 멀티 region 확장 시 outbox 동기화 문제 — 현재 single region 이므로 무관.

결정 #6 · iOS → GCS 직접 업로드 (presigned PUT)

대안: API 가 multipart 받아서 GCS 에 relay. 이유: API 가 이미지 트래픽을 안 처리해도 됨 → Cloud Run 메모리/timeout 압박 감소. 대가: presigned URL 의 prefix 검증을 정확히 해야 cross-tenant 누설 방지 — 기존 domain rule 로 강제됨.

결정 #7 · AI = Gemini 3.1 Flash-Lite (Preview, 사용자 검증)

대안: 2.5 Flash (구형, 사용자 reject), 3 Flash GA ($47/월), 3.5 Flash ($140/월). 이유: 가장 싸고 빠르며 3.x 최신. 사용자가 다른 프로젝트에서 실사용해 안정성 확인. 대가: Preview 단계라 SLA 미보장 — 추상화 layer 로 모델 교체 비용 낮춤. asia-northeast1 가용성 (§openq-1).

결정 #8 · 인증 = 자체 JWT (KMS 서명)

대안: Firebase Authentication, Identity Platform. 이유: iOS 측이 이미 Apple/Google SDK 로 ID token 받음. 자체 JWT 면 dev/prod 일관. KMS 위임으로 키 노출 없음. 대가: Firebase 의 user management UI / 분석 기능 직접 구현 필요 — 모찌 규모에서 불필요.

결정 #9 · Cloud NAT 없이 시작

대안: Cloud NAT + 고정 IP. 이유: $35/월 비용 + WebFetchTool 의 outbound 대상이 allowlist 강제하는 사이트 거의 없음. Cloud Run 기본 egress 가 가변 IP 라도 SSRF 가드는 호스트 정책 + IP 검증이라 무관. 대가: 특정 사이트에서 IP 차단 받으면 그 때 도입. 전환 임계: WebFetch 실패율 5% 초과 시.

결정 #10 · Housekeeper = 1 시간 cron (5분 아님)

대안: 5분 cron, 또는 background task 안에 합치기. 이유: knowledge decay · idempotency TTL · DLQ alert 모두 시간 민감하지 않음. 1 시간이면 충분. schedule_ended 자동 archive 는 1 시간 지연 가능 — 사용자가 캡쳐 다시 열 때 lazy 평가로 즉시 처리. 대가: 거의 없음.

09 — Open questions

미결정 · 알아볼 부분

openq-1 · Gemini 3.1 Flash-Lite 의 asia-northeast1 가용성

질문: Vertex AI Tokyo 에 3.1 Flash-Lite Preview 가 서빙되는지. multimodal + function calling 모두 지원되는지.
왜 중요한가: us-central1 vs Tokyo 의 RTT 차이 ~100ms × 6K calls/월 = 600s 누적 latency.
어떻게 결정: gcloud ai models list --region=asia-northeast1 또는 콘솔 확인. 없으면 us-central1.

openq-2 · Cloud Run timeout=3600s vs SSE 실제 연결 길이

질문: Cloud Run 의 max timeout 3600s (1시간) 는 SSE 연결에 충분한가? iOS 가 background 로 가면 connection 끊기는데, 재연결시 catch-up 흐름은?
어떻게 결정: iOS 측 SSE 클라이언트가 disconnect 감지 + exponential backoff 재연결. 서버는 idempotent state push 만 — 같은 node 이벤트 두 번 받아도 안전.

openq-3 · 민감 캡쳐의 자연어 검색 포함 여부

질문: sensitivity ≥ 9 캡쳐는 서버 업로드 거부 → 서버 embedding 없음. 사용자가 검색해도 안 잡힘. 온디바이스 검색 인덱스 둘지?
어떻게 결정: PRIVACY_SENSITIVE_CAPTURE.md §9. iOS sqlite + Apple NL embedding 로 로컬 검색. 별도 design doc.

openq-4 · 서버 측 마스킹된 이미지 저장 여부

질문: mochi-temp-redacted 버킷을 24h TTL 로 둘 가치가 있나? semantic payload 만으로 분류 정확도 충분한가?
어떻게 결정: 베타 5명에게 양쪽 분기 비교. 정확도 차이 5% 이내면 텍스트만 전송.

openq-5 · agent_runs · tool_calls 의 input/output PII

질문: tool_calls.input_json / output_json 에 민감정보가 들어갈 수 있음. CMEK 없이 기본 암호화로 충분한가?
어떻게 결정: 개인정보처리방침 검토 후. MVP 는 기본 암호화 + log redaction, 필요시 column-level (pgcrypto) 도입.

openq-6 · DAU 100 가정이 깨지는 시점의 대응

질문: 콘테스트 시연 후 갑작스런 DAU 1K spike 가 오면? 본 MVP 가 견디나?
어떻게 결정: db-g1-small + Cloud Run max=3 으로는 DAU 200 이 안전 천장. 임계 경보 SLO 설정 (DB CPU > 70% for 10 min) → 자동 메시지 + 수동 scale up. P1 단계 (§로드맵) 의 변경 사전 준비.
