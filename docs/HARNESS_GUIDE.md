# 모찌 하네스 가이드 — 처음 합류한 팀원을 위해

> 이 문서는 "하네스가 뭔가요?", "왜 우리는 이렇게 일하나요?", "오늘 첫 작업을 어떻게 시작하나요?" 에 답하는 입문서입니다. 30분 정도면 다 읽힙니다. 운영 규칙의 *공식 원천*은 [`docs/WORKFLOW.md`](WORKFLOW.md) 이고, 이 가이드는 그걸 풀어 쓴 친절 버전이에요.

---

## 1. 우리는 왜 이렇게 일하나 — 출발점

### 옛날 방식 (역할 기반 분담)

```
백엔드 담당자 ─ API 명세 작성 ─→ 프론트엔드 담당자 ─→ 그걸 보고 화면 개발
                       ↓                                      ↓
                    AI 로 개발                              AI 로 개발
```

이게 *AI 시대* 에 오면 갑자기 비효율이 폭발합니다.

- 백엔드가 AI 에게 *명세를 만들게* 하는 동안, 프론트엔드는 *기다린다.*
- 명세가 전달돼도 프론트엔드 AI 는 "이게 정확히 뭘 의미하지?" 를 다시 묻는다.
- 명세가 바뀌면 *사람을 통해* 다시 전달된다. AI 끼리 동기화가 안 된다.
- 결국 사람이 **번역기 노릇**을 하느라 시간을 다 쓴다.

### 우리 방식 (Feature 기반 풀스택 분담)

```
A 가 알림 기능 통째로 (백엔드 + iOS) ─ AI 로 개발
B 가 게시판 기능 통째로 (백엔드 + iOS) ─ AI 로 개발
C 가 검색  기능 통째로 (백엔드 + iOS) ─ AI 로 개발
                  ↓
       AI 끼리 같은 규칙·문서·계약을 보고 알아서 맞춘다
                  ↓
            AI 가 검증까지 한다
```

한 사람이 자기 기능의 **위에서 아래까지 다** 만집니다. 사람이 번역기가 되지 않습니다.

### 그러면 무엇이 필요한가

세 명이 각자 자기 AI 로 다른 부분을 짜면, **그 결과물이 서로 안 어긋나야** 합니다. 안 어긋나려면:

1. **모두가 같은 규칙을 본다** — 네이밍, 파일 위치, 코드 스타일이 한 군데에서 결정.
2. **모두가 같은 계약을 본다** — API 모양(`openapi.json`), 도메인 모델, 데이터 흐름.
3. **모두가 같은 작업 흐름을 따른다** — 계획 → 코드 → 검증 → 문서 동기화 → 커밋.
4. **AI 가 이 모든 걸 이해할 수 있어야 한다** — 그래서 *문서* 가 사람뿐 아니라 *AI 가 읽기 좋은 모양*으로 정리돼야 한다.

**하네스(harness)** 는 이 네 가지를 가능하게 만든 *작업 환경 전체* 를 부르는 이름입니다.

## 2. 한 장으로 보는 그림

```
┌─────────────────────────────────────────────────────────────┐
│  사람 (당신)                                                  │
│   ↓ 작업 지시 ("알림 기능 만들어줘")                              │
│                                                              │
│  Claude Code (부모) ─── 코드 수정의 유일한 주체                  │
│   │                                                          │
│   ├─ doc-guardian  ── 작업 전 문서 모순 검사 (read-only)       │
│   ├─ architect     ── 검증 가능한 플랜 작성 (read-only)         │
│   ├─ code-reviewer ── 리뷰, codex 위임 (read-only)            │
│   ├─ qa-validator  ── 테스트·동작 확인 (read-only)             │
│   └─ lab-experimenter ─ lab/ 안에서 실험 (유일하게 write)        │
│                                                              │
│  codex (검증 엔진) ── code-reviewer/qa-validator 가 호출         │
│                                                              │
│  문서들 (docs/, CLAUDE.md, AGENTS.md, journal/)                │
│   └─ 모든 AI 가 같은 규칙을 본다                                 │
└─────────────────────────────────────────────────────────────┘
```

용어 풀이:
- **하네스(harness)**: AI 가 일하기 좋게 만들어둔 작업 환경 전체. `.claude/` 폴더 + 문서들 + 규칙들 + 슬래시커맨드.
- **서브에이전트(sub-agent)**: 특정 일만 잘하도록 좁힌 작은 AI. doc-guardian, architect 같은 친구들.
- **codex**: OpenAI 의 코딩 AI. 우리는 *검증 엔진* 으로만 씁니다 (코드 수정 X, 리뷰/QA O).
- **정합성(consistency)**: 여기저기 흩어진 정보가 서로 어긋나지 않은 상태.
- **폭포(cascade)**: 위 문서를 바꾸면 아래 문서도 따라 바꿔야 한다는 규칙.

## 3. 저장소 둘러보기

```
mochi/
├─ CLAUDE.md           ← Claude(우리 주 AI) 가 매번 읽는 정체성·원칙
├─ AGENTS.md           ← codex 가 매번 읽는 거. CLAUDE.md 의 미러(거울)
│
├─ docs/               ← 모든 공식 문서. 안정도(level) 로 분류돼 있음
│  ├─ WORKFLOW.md      ← L1 운영 매뉴얼. 안 바뀜.
│  ├─ PRODUCT.md       ← L1 제품 정의.
│  ├─ ARCHITECTURE.md  ← L2 시스템 구조
│  ├─ DOMAIN_DESIGN.md ← L2 도메인 모델·DB
│  ├─ PRIVACY_*.md     ← L2 민감 정보 처리
│  ├─ TODO.md          ← L3 할 일
│  ├─ CHANGELOG.md     ← L3 변경 이력
│  └─ HARNESS_GUIDE.md ← (이 문서) 친절한 입문서
│
├─ journal/            ← 하루 작업 로그 + 인수인계
├─ .claude/            ← 서브에이전트·슬래시커맨드 정의
│  ├─ agents/
│  ├─ commands/
│  └─ settings.json
│
├─ mochi-ios/          ← iOS 앱 (별도 git)
├─ mochi-backend/      ← FastAPI 백엔드 (별도 git)
├─ lab/                ← 실험·벤치마크 (자유)
└─ archive/            ← 폐기된 문서. 안 읽음.
```

> **꼭 기억할 것**: 루트(`mochi/`) 자체는 git 이 *아닙니다.* `mochi-ios/`, `mochi-backend/` 만 각자 git 입니다. 곧 모노레포로 합칠 예정이지만, 그때까지는 루트 파일(`docs/`, `journal/`, `.claude/`) 은 *팀 안에서 직접 공유* 가 필요해요.

## 4. 문서의 등급 — L1 / L2 / L3

문서마다 **"얼마나 자주 바뀌는가"** 가 다릅니다. 자주 바뀌는 문서와 안 바뀌는 문서를 같이 두면 헷갈리니까, **변화 속도로 등급을 매겼습니다.**

| 등급 | 성격 | 어떤 문서 | 누가 바꿀 수 있나 |
|---|---|---|---|
| **L1** | 거의 안 바뀜 | `WORKFLOW.md`, `PRODUCT.md` | 팀 합의 + 사람 명시 승인 필요. AI 단독 수정 금지. |
| **L2** | 바뀌면 골치 아픔 | `ARCHITECTURE.md`, `DOMAIN_DESIGN.md`, `PRIVACY_*.md` | 코드 변경과 짝지어 함께 수정. 하위 문서까지 함께 동기화. |
| **L3** | 자주 바뀜 | `TODO.md`, `journal/*`, `CHANGELOG.md` | 자유. 매일 채워나감. |

### 폭포 규칙 — 위가 바뀌면 아래도 따라

```
L1 바뀜 → L2 검토 필요 → L3 검토 필요
       (예: PRODUCT 의 핵심 가치가 바뀌면 DOMAIN 도 검토)

L2 바뀜 → 코드 / iOS·BE README / 이번 주 plan 동기화 필요
       (예: DB 스키마 바뀌면 백엔드 코드, iOS 코드, READMEs 모두 함께 갱신)
```

이걸 `doc-guardian` 서브에이전트가 작업 전에 자동 체크합니다. 안심하세요.

## 5. AI 가 어떤 문서를 읽을지 — Read 의 룰

이게 사용자(개발자) 가 가장 자주 묻는 부분입니다.

### 무조건 읽는 것 (필수 컨텍스트)

- `CLAUDE.md` — Claude 가 자동으로 매 세션 시작 시 읽음
- `AGENTS.md` — codex 가 자동으로 매 호출 시 읽음
- 작업이 닿는 *영향 범위* 의 문서:
  - 도메인 작업 → `docs/DOMAIN_DESIGN.md`
  - 시스템 토폴로지·API 작업 → `docs/ARCHITECTURE.md`
  - 민감 정보 관련 작업 → `docs/PRIVACY_SENSITIVE_CAPTURE.md`

### 선택적으로 읽는 것 (필요할 때만)

- `journal/*` — 과거 결정 배경 확인할 때만
- `lab/*` — 실험 결과 참고할 때만
- `docs/CHANGELOG.md` — 최근 변경 맥락 필요할 때만
- `archive/*` — **거의 안 읽음.** 이미 폐기된 문서.

### 자동으로 *안* 읽는 것

- `archive/**` — 폐기 문서. 명시적으로 요청해야만 열림.

> **왜 이렇게 나눴는가**: AI 의 컨텍스트 윈도우(한 번에 읽을 수 있는 양) 가 제한돼 있습니다. 안 읽어도 되는 걸 자동으로 안 읽게 만들면, *읽어야 할 것* 에 더 집중할 수 있어요.

## 6. 하루 작업 동선

당신이 "알림 기능 만들어줘" 라고 Claude 에게 말했다고 가정합시다. 그 뒤에 무슨 일이 일어나는지:

```
[1] 작업 지시
     ↓
[2] doc-guardian 이 먼저 일함
     - 알림 관련 문서들이 서로 안 어긋나는지 검사
     - 모호하면 STOP, 당신에게 물음
     ↓
[3] architect 가 플랜을 짬
     - "이 작업의 검증 기준은 무엇인가" 명확히
     - 공유 영역(API 계약, DB 스키마 등) 건드리면 경고
     - 더 단순한 길이 있으면 제안
     ↓
[4] Claude(부모) 가 실제 코드 수정
     - 서브에이전트는 이걸 못 함, Claude 만 함
     ↓
[5] code-reviewer 가 리뷰 (codex 위임)
     - 잘못된 점 찾으면 Claude 가 고침. 통과까지 반복.
     ↓
[6] qa-validator 가 동작 확인 (codex 위임)
     - `make test`, `tuist test` 같은 검증 실행
     ↓
[7] 문서 동기화 (정합성 폭포)
     - 코드 바뀐 만큼 docs 도 따라 갱신
     - CHANGELOG 에 한 줄 추가
     ↓
[8] /ship 슬래시커맨드 — 마지막 체크
     ↓
[9] 커밋 (Conventional Commits 포맷)
```

각 단계는 자동입니다. 당신은 [1] 만 하고, [2]에서 모호한 게 있으면 답해주고, [9] 의 커밋만 확인해주면 됩니다.

## 7. 슬래시커맨드 사용법

Claude Code 에서 `/` 로 시작하는 명령어들입니다. 자주 하는 일을 묶어둔 거예요.

| 명령어 | 언제 쓰나 | 예시 |
|---|---|---|
| `/daily [주제]` | 오늘 한 일을 journal 에 기록 | `/daily 알림 기능 진행` |
| `/handoff [주제]` | 미완 작업을 다음 세션이 이어받게 인수인계 | `/handoff 알림 백탭 흐름` |
| `/ship ios\|backend` | 머지 전 마지막 체크 (테스트·린트·문서) | `/ship backend` |
| `/codify "<갈라진 결정>"` | 발견한 갈라짐을 규칙으로 굳히기 | `/codify "get_ vs fetch_ 명명"` |
| `/sync-agents` | CLAUDE.md → AGENTS.md 미러 재생성 | `/sync-agents` |

### 가장 자주 쓸 명령어

- **하루 시작할 때**: 명령어 안 씀. `git pull` 하고 `journal/` 최신 항목 훑어보기.
- **작업 끝낼 때**: `/ship <범위>` → 통과하면 커밋.
- **세션 끝나는데 미완일 때**: `/handoff <주제>` 그리고 `/daily`.

## 8. 우리 모두 지킬 작업 원칙 4가지

이건 사람도 AI 도 똑같이 지킵니다. `CLAUDE.md` 의 §1~§4 와 같아요.

### ① Think Before Coding (코딩하기 전 생각하기)
- 가정을 명시. 헷갈리면 묻기.
- 해석이 여러 갈래면 모두 제시. 조용히 하나 고르지 않기.
- 모호하면 멈추고 짚어주기.

### ② Simplicity First (단순함 우선)
- 요청 안 한 기능 안 만들기.
- 한 번만 쓰는 코드에 추상화 X.
- "시니어가 보면 과설계라 할까?" 라고 자문. yes 이면 단순화.

### ③ Surgical Changes (외과적 변경)
- 부탁 안 받은 주변 코드 안 만지기.
- 망가지지 않은 거 리팩터링 X.
- 너라면 다르게 짤 만한 부분도 *기존 스타일* 따르기.

### ④ Goal-Driven Execution (목표 검증 가능하게)
- "검증 추가" → "잘못된 입력에 대한 테스트가 통과한다."
- "버그 수정" → "버그를 재현하는 테스트가 통과한다."
- 검증 기준을 먼저 정하고 그걸 만족시키는 방향으로 작업.

## 9. 문서를 어떻게 쓸까 (당신이 직접)

문서를 추가하거나 수정할 때:

1. **어느 등급(L1/L2/L3)에 해당하나** 생각하기.
2. 새 파일이면 **front-matter** 박기:
   ```yaml
   ---
   level: 2
   description: 한 줄 설명. 이 문서가 무엇이고 누가 언제 읽나.
   ---
   ```
3. L1/L2 를 바꿨으면 **하위 문서도 함께 갱신** (폭포 규칙).
4. 의미 있는 변경이면 **`docs/CHANGELOG.md` 맨 위에 한 줄 추가**:
   ```
   ## 2026-05-29 — backend
   - 알림 기능 추가. POST /notifications. (이유: ...)
   ```

> **CHANGELOG 가 중요한 이유**: 나중에 "왜 이렇게 됐지?" 물어볼 때, CHANGELOG 가 단일 원천이 됩니다. journal 은 *과정* 이지만 CHANGELOG 는 *결과* 입니다.

## 10. 막혔을 때 / 미완 작업 / 다음 세션 인수인계

작업이 안 끝났는데 시간이 다 됐을 때:

```bash
/handoff 알림-백탭-흐름
```

이러면 `journal/2026-05-29-알림-백탭-흐름-handoff.md` 가 만들어집니다. 다음에 누가 (당신이든, 다른 팀원이든, AI 든) 그 파일만 보면 *0부터* 그대로 이어받을 수 있어요. 무엇을 결정했고, 무엇이 미정이고, 다음에 뭘 해야 하는지가 다 적혀 있습니다.

## 11. 자주 묻는 질문

### Q1. 서브에이전트(architect 등) 가 코드를 못 만진다고요?
네. **일부러** 그렇게 막아뒀습니다. 사고 한 번이 큰 손실로 이어질 수 있어서, *코드 수정의 주체는 부모 Claude 한 명* 으로 좁혔어요. 서브에이전트는 분석·평가·검증만 합니다.

### Q2. codex 와 Claude 는 뭐가 다른가요?
- **Claude**: 우리의 주된 작업자. 계획·코드·문서 모두.
- **codex**: 검증 전용. code-reviewer, qa-validator 가 *codex 에게 한 번 더 봐달라* 고 위임할 때만 호출됨. 외부 second opinion.

### Q3. 백엔드를 만지는데 iOS 문서까지 봐야 하나요?
*공유 표면* 을 만질 때만요. 공유 표면이란:
- API 계약 (`openapi.json`)
- DB 스키마
- 양쪽이 같이 쓰는 도메인 모델
- 라우팅·네비게이션
- 디자인 토큰

이 다섯 군데는 한쪽 만지면 다른 쪽도 검토해야 합니다. 그 외엔 자기 영역만 보면 돼요.

### Q4. 다른 팀원이 만든 규칙과 내 규칙이 다르면?
`/codify "<갈라진 결정>"` 슬래시커맨드를 씁니다. 갈라짐을 발견할 때마다 *가장 싼 통제 티어* 로 굳혀요 (린터·문서·생성기 중 하나). 미리 모든 규칙을 적어두지 않고, *발견될 때만* 추가합니다. (그래서 규칙도 Simplicity First.)

### Q5. AI 가 시킨 일과 다른 걸 하면?
즉시 멈추고 짚어주세요. CLAUDE.md §1 의 "모호하면 멈춘다" 가 발동 안 한 거예요. 무엇이 모호했는지 함께 확인하고, 필요하면 `/codify` 로 룰을 추가합니다.

### Q6. 이 문서들이 너무 많아요. 어디부터 봐야 하나요?
다음 순서를 권장합니다.

1. 이 가이드 (`HARNESS_GUIDE.md`) — 큰 그림
2. `docs/PRODUCT.md` — 우리가 무엇을 만드나
3. `docs/WORKFLOW.md` — 운영 룰 (이 가이드의 더 단정적인 버전)
4. 자기 작업이 닿는 L2 문서 한 개 — `DOMAIN_DESIGN.md` 또는 `ARCHITECTURE.md`
5. 어제·오늘의 `journal/` — 최근 무슨 일이 있었나

`CHANGELOG.md` 는 *변경이 궁금할 때만* 펴면 됩니다. 처음부터 다 읽지 마세요.

## 마치며

이 하네스의 핵심 사고를 한 문장으로 줄이면 이렇습니다.

> **"우리가 갈라질 수 있는 모든 결정을 가장 싼 도구로 미리 막아두면, AI 가 그 위에서 자유롭게 일할 수 있다."**

규칙이 많아 보일 수 있지만, 대부분은 *AI 가 자동으로 처리* 합니다. 당신이 직접 챙길 건 다음 다섯 가지뿐이에요:

1. 작업 시작 전 `git pull` 하고 `journal/` 최신 훑기
2. 작업 지시할 때 *명확하게* (모호하면 AI 가 물어볼 거예요)
3. 작업 끝나면 `/ship`
4. 미완이면 `/handoff`
5. 발견한 갈라짐은 `/codify`

나머지는 하네스가 알아서 합니다. 모르는 게 생기면 다른 팀원이나 Claude 에게 물어보세요 — 그게 이 시스템의 정상 작동 방식입니다.
