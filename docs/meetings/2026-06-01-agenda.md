# 2026-06-01 회의 안건

> 목표: 프로젝트 본격 시작 전에 **확정해야 업무가 빨라지는 L1 결정 + 바로 영향 있는 L2 결정**을 정한다.

## 0. 현재 확인된 사실

- 제출 마감은 `2026-07-15`.
- 현재 운영 모드는 2주 sprint x 4회 압축 모드다.
- 제품 정본은 "스크린샷, 링크, 텍스트 메모를 AI가 일정·할 일·지식·기록으로 분류하고 다시 찾아주는 iOS 기록 관리 앱"이다.
- 현재 IA 가안은 홈 / 질문 / 모찌들 / 검색이다.
- 현재 입력 경로는 백탭, Share Extension, Siri/Spotlight QuickCapture, 홈 quick memo다.
- 현재 서버 흐름은 ingest → outbox → worker → Gemini agent → `intent/candidates/summary/entities` 저장이다.
- 현재 구현에는 `mochi_items`, `mochi_item_image_refs`, `entities`, `embeddings`, `idempotency_keys`, `agent_runs`, `tool_calls` 중심만 있다.
- `mochi_action_candidates`, `todos`, `calendar_events`, `knowledge_summaries`, `memos`는 설계에는 있으나 실제 구현은 아직 없다.
- 검색/RAG는 구조는 있으나 embedding 적재와 실제 query embedding 품질은 아직 약하다.
- SSE, 서버 intent override PATCH의 iOS 연결, sync catch-up은 미구현 또는 known drift다.
- `DOMAIN_DESIGN.md` 일부는 현재 구현(as-built)과 다르다. 이번 회의에서 "지금 구현할 정본 스키마"를 다시 확정해야 한다.

## 2. 미션 / 비전 / 데모 범위

### 결정할 것

- 모찌가 가장 잘해야 하는 한 가지가 무엇인가.
- 데모에서 반드시 보여줄 P0 시나리오 2~3개는 무엇인가.
- 마감 전까지 버릴 P1/P2는 무엇인가.

### 아이디어

- 핵심 문장: "저장은 한 번, 정리는 자동, 회수는 자연어."
- 데모 P0:
  - 백탭 스크린샷 저장 → 자동 분류 → 홈 카드 반영
  - URL 공유 → 요약·분류 → 질문 탭에서 다시 찾기
  - 메모 입력 → 할 일/일정/기록 자동 정리
- P1/P2 후보:
  - 완전한 캘린더 동기화
  - APNs 기반 백그라운드 완료 알림
  - 고도화된 개인화
  - 완전한 멀티디바이스 sync

## 3. 하네스 엔지니어링 / 협업 원칙

  - DB migration

- 하네스 설명 포인트:

## 5. 탭 구조와 화면 책임

### 결정할 것

- 탭 4개를 유지할지.
- "모찌들"이 캘린더인지, 전체 기록 리스트인지.
- 검색과 질문을 분리할지 합칠지.

### 아이디어

- 홈:
  - 오늘 볼 것
  - 분석중
  - 헷갈려요
  - 최근 기록
- 질문:
  - 자연어 RAG
  - 예: "지난주 AI Agent 자료 정리해줘."
- 모찌들:
  - 날짜/intent 기반 browse
  - 캘린더 뷰는 이 탭 안의 한 모드
- 검색:
  - 키워드/필터 중심 빠른 찾기
  - 질문은 답변 생성, 검색은 item 찾기
- 일정이 촉박하면 검색과 질문을 합칠 수 있다. 데모 가치는 질문 탭이 더 크다.

## 6. 4-Intent / 복수 Intent 정책

### 결정할 것

- 4-Intent를 유지할지.
- 하나의 `MochiItem`에 복수 intent를 저장할지, 여러 item으로 쪼갤지.
- confidence가 높을 때 자동 materialize할지.

### 제안

- 4-Intent는 유지한다. 제품 설명, 코드, 문서가 이미 여기에 맞춰져 있다.
- 입력 1건 = `MochiItem` 1개를 유지한다.
- 복수 의도는 `secondary_intents`, `intent_applicability`, `intent_candidates`로 보관한다.
- item을 여러 개 만들지 말고, 실행 단위는 `mochi_action_candidates`, `todos`, `calendar_events`, `knowledge_summaries`로 분리한다.
- high confidence는 자동 정리하고, low confidence만 "헷갈려요"로 사용자에게 묻는다.

## 8. 자동화 vs 사용자 확인

### 결정할 것

- AI가 바로 정리해도 되는 기준을 어떻게 잡을지.
- 유저에게 매번 승인 액션을 요구할지.
- "수정/되돌리기" 중심 UX로 갈지.

### 아이디어

- 매번 승인 요구는 모찌의 핵심 가치와 충돌할 수 있다.
- 기본 정책:
  - high confidence: 자동 정리
  - medium confidence: 정리하되 needs-review 표시
  - low confidence: "헷갈려요" 카드
- schedule은 intent confidence만으로 자동 생성하면 위험하다. 날짜/시간 필드 품질까지 봐야 한다.
- todo는 due date가 없어도 생성 가능한지 실험으로 정한다.
- UX는 "승인"보다 "모찌가 정리했어요 → 수정 / 되돌리기"가 자연스럽다.

## 9. 이번 주 실험

### 결정할 것

- 이번 주에 무엇을 실험으로 검증할지.
- threshold를 감으로 정하지 않기 위한 eval dataset 범위.

### 제안

- 데이터셋:
  - 스크린샷 50개
  - URL 50개
  - 메모 50개
- 사람이 라벨링할 것:
  - primary intent
  - secondary intent
  - 자동 materialize 가능 여부
  - 필요한 필드: 날짜, 제목, task, URL, summary 등
- threshold sweep:
  - intent auto threshold: 0.6 / 0.7 / 0.8 / 0.9
  - schedule은 `startAt` 없으면 자동 calendar 금지
  - todo는 due date 없어도 생성 가능한지 비교
- 측정 지표:
  - intent accuracy
  - high-confidence precision
  - 자동 처리율
  - 사용자 review 필요율
  - schedule/todo 필드 추출 정확도

## 13. 추가 안건

### 민감 캡처 정책

- 원본 이미지 업로드 기본값을 정해야 한다.
- OCR/마스킹 MVP 범위를 정해야 한다.
- 점수 6 이상 민감 캡처는 어떤 UX로 처리할지 결정해야 한다.

### 실패 UX

- 분석 실패
- 네트워크 실패
- low confidence
- 서버 지연
- 재시도 버튼과 자동 재시도 범위

### 데모 데이터 전략

- 실제 개인정보 없는 샘플을 누가 만들고 관리할지 정한다.
- 실험 데이터와 발표 데모 데이터를 분리한다.
- `lab/data/`는 git 추적 제외를 유지한다.

## 14. 회의 결론 후보
