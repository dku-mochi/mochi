# 모찌(MOCHI) — 제품 정의

> Multimodal AI 기반 스크린샷·링크·기록 통합관리 에이전트
> 2026 SW중심대학 디지털 경진대회 / 팀 **세얼간이** (송준서·박세현·이용찬)

> 이 문서는 **L1(불변 기반)** — 제품의 *왜*와 *무엇*만 소유한다. *어떻게 보이는가*(화면·시나리오·디자인)는 [`UX_SPEC.md`](UX_SPEC.md)(L3), *어떻게 저장되는가*(도메인·스키마·lifecycle)는 [`DOMAIN_DESIGN.md`](DOMAIN_DESIGN.md)(L2) 가 소유한다.

## 1. 서비스 개요

### 1.1 이름

**모찌(MOCHI)**

서비스명은 두 문장에서 가져온다:
- "뭐든지 찍어보세요."
- "이거 뭐였지?"

사용자가 캡처하거나 저장해둔 정보를 나중에 다시 찾고 활용할 수 있도록 돕는 AI 기록 관리 에이전트.

### 1.2 한 줄 소개

> 모찌는 스크린샷, 링크, 텍스트 메모를 AI 가 자동으로 분석해 일정·할 일·지식·기록으로 분류하고 다시 찾아주는 iOS 기반 멀티모달 기록 관리 앱이다.

### 1.3 핵심 가치

사용자는 이미 많은 것을 저장한다. 문제는 저장 이후다.

저장은 쉽지만, 다시 찾고 활용하는 것은 어렵다. 모찌는 이 문제를 다음 원칙으로 해결한다:

> **입력은 더 쉽게, 분류와 회수는 AI 가.**

### 1.4 컨셉 문장

> 모찌는 사용자가 저장한 정보를 단순히 보관하는 앱이 아니라, AI 가 기록의 의도와 생명주기를 이해해 다시 활용 가능한 지식으로 바꿔주는 iOS 기록 관리 에이전트다.

짧은 버전:

> 뭐든지 찍어보세요. 모찌가 기억하고 정리해드릴게요.

### 1.5 미션

> **놓치기 쉬운 순간은 쉽게 남기고, 필요한 기억은 쉽게 떠오른다.**

모찌가 존재하는 이유이자 **제품 의사결정의 기준**. 입력(순간을 남김)과 회수(기억이 떠오름) 양쪽의 마찰을 함께 없애, 사용자가 저장한 것이 다시 살아 쓰이게 한다. §1.3 핵심 가치("입력은 더 쉽게, 분류와 회수는 AI 가")의 정서적 선언이다.

**"떠올린다"가 아니라 "떠오른다"** — 회수의 능동 주체는 사용자가 아니라 모찌다. 사용자가 직접 찾고 정리하게 만드는 설계는 미션에 반한다. 이 차이가 기능 결정 시 리트머스다.

## 2. 문제 정의

### 2.1 사용자 문제

사용자는 일상에서 정보를 빠르게 저장하지만, 저장 위치가 여러 앱에 분산되어 있다.

- 유튜브 영상을 나중에 보려고 저장했지만 잊어버림
- 카카오톡으로 받은 링크를 다시 찾기 어려움
- 스크린샷은 많지만 왜 찍었는지 기억나지 않음
- 학교 과제를 캡처해두었지만 마감일을 놓침
- 메모·사진·캘린더·브라우저 북마크가 각각 따로 움직임
- 저장한 정보가 일정인지·할 일인지·학습 자료인지 사용자가 직접 분류해야 함

### 2.2 기존 도구의 한계

| 기존 도구 | 장점 | 한계 |
|---|---|---|
| 카카오톡 나에게 보내기 | 빠르게 저장 가능 | 시간순으로 쌓여 찾기 어려움 |
| 인스타그램 저장 | 콘텐츠 저장 쉬움 | 인스타 내부 콘텐츠에 한정 |
| 유튜브 나중에 볼 동영상 | 영상 저장 쉬움 | 영상 내용 기반 검색 어려움 |
| 사파리 책갈피 | 웹페이지 저장 가능 | 사용자가 직접 폴더 관리 필요 |
| iOS 사진앱 | 스크린샷 자동 보관 | 왜 찍었는지 맥락 파악 어려움 |
| 메모앱 | 자유롭게 작성 가능 | 분류와 회수는 수동 |

모찌는 이 문제를 **단일 입력 경로 + AI 자동 분류 + 자연어 회수** 로 해결한다.

## 3. 제품 목표

모찌의 제품 목표는 세 가지:

1. 사용자가 어떤 앱에서든 기록을 쉽게 저장할 수 있게 한다.
2. AI 가 기록의 의도를 파악해 자동으로 분류한다.
3. 사용자가 나중에 자연어로 기록을 다시 찾고 활용할 수 있게 한다.

### MVP 우선순위

| 우선순위 | 기능 |
|---|---|
| P0 | iOS 앱 로그인 (Apple / Google OAuth) |
| P0 | 온보딩 튜토리얼 (모찌 소개·백탭·공유 저장 안내) |
| P0 | 홈 화면 (회수 진입점·주간 리포트·최근 모찌) |
| P0 | 백탭용 입력 모달 (메모 / 스크린샷) |
| P0 | Share Extension (이미지·텍스트·링크 수신) |
| P0 | 4-Intent 분류 (일정·할 일·지식·기록) |
| P0 | 모찌 상세 페이지 (AI 요약·원본·액션) |
| P1 | 자연어 회수 (Hybrid Search + RAG 답변) |
| P1 | 캘린더 (날짜별 기록·일정·할 일 탐색) |
| P2 | 알림 (분석 완료·헷갈려요 Live Activity) |
| P2 | 캘린더 — 확신 시 앱 내부 캘린더에 능동 등록(미확신 시 확인). 시스템 캘린더(EventKit) 연동은 추후 |

## 4. iOS 플랫폼 전략

### 4.1 Share Extension 기반 입력

iOS Share Extension 으로 이미지/스크린샷·텍스트·URL·일부 앱의 미디어 메타데이터를 받는다. Share Extension 은 별도 프로세스로 실행되며, App Group + shared container + 서버 업로드 큐 설계가 필요하다.

### 4.2 백탭(Back Tap) 기반 입력

아이폰 뒷면을 두 번 또는 세 번 탭해 단축어 실행. 모찌는 시스템 레벨에서 직접 제어하지 않고 **사용자가 Shortcuts 를 등록하고 뒷면 탭에 연결하도록 안내**한다 — 단축어 *추가* 와 뒷면 탭 *연결* 은 분리된 두 행동이라, 온보딩이 체크리스트로 끝까지 끌고 간 뒤 **실제 백탭이 모찌에 도달하는지 검증**한다 (UX_SPEC §3.3).

뒷면 탭 설정 화면으로 가는 공식 딥링크는 없다 — 비공식 `App-Prefs:` 는 iOS 17/18 에서 동작하지 않고 심사 리스크가 있어, 경로를 시각 가이드로 안내하고 딥링크는 best-effort(미래 iOS 대비 방어 코드)로만 시도한다.

### 4.3 OAuth 로그인

- Apple 로그인 (프라이버시 친화)
- Google 로그인 (Google Sign-In for iOS)

## 5. 내부 처리 모델 — 4-Intent

모찌는 모든 기록을 내부적으로 4가지 Intent 로 분류한다. **이것은 사용자에게 가르치는 분류 체계가 아니라, "모찌가 어떻게 처리했냐"의 백엔드 모델이다** — 사용자에게 중요한 것은 "어떤 일정이 언제 잡혀 있고, 뭘 해야 하고, 모찌가 언제 다시 알려주는지"이고, 4-Intent 는 그것을 가능하게 하는 배관이다 (§8 UX 원칙).

| Intent | 설명 | 예시 | 생명주기 |
|---|---|---|---|
| **일정** (schedule) | 특정 시간에 발생하는 이벤트 | 내일 3시 팀 회의 | 시간 도래 후 완료/기록화 |
| **할 일** (todo) | 완료 여부가 중요한 작업 | 보고서 제출하기 | 완료 전까지 활성 |
| **지식** (knowledge) | 다시 학습·참고할 정보 | RAG 구조 설명 글 | 장기 보관, 시간 지나면 decay |
| **기록** (memo) | 맥락 보존이 중요한 메모 | 회의 내용, 감상, 일상 | 영구 보관 |

### Intent 별 처리

**일정** — 날짜/시간 추출 → 캘린더 등록 후보, 알림 후보 생성
**할 일** — 작업명·마감일·우선순위 추정 → 체크리스트 생성
**지식** — 핵심 주제·요약·태그 추출 → 임베딩 저장, 자연어 검색 대상
**기록** — 원본 맥락 보존, 간단 요약 → 날짜별 타임라인 저장

### 생명주기

모찌의 차별점은 "저장 시점" 뿐 아니라 "저장 이후" 까지 관리한다는 점:

- "내일 3시 팀 회의"는 회의 전에는 알림 중요, 회의 후에는 기록으로 전환
- "보고서 제출"은 완료 전 홈에 계속 제안, 완료 후 archived
- "RAG 구조 설명 글"은 시간 지나도 검색 가치, 장기 보관
- 한 기록이 여러 의도를 동시에 가질 수 있고(예: 일정이자 할 일), 각 의도는 서로 독립적으로 생명주기를 밟는다

> 상태머신·전이 규칙의 정본은 `DOMAIN_DESIGN.md` §5.

### 노출 원칙 — Intent 는 배관이다

4-Intent 는 검색·캘린더·알림·생명주기의 **배관**으로 쓰고, 화면에는 분류 체계로 강조하지 않는다:

- 사용자에게 "모찌가 4가지로 분류했어요"라는 메타 노출 금지 — 분류는 행동(체크박스/캘린더 통지/링크 열기)의 *형태*로만 드러난다.
- 단, "일정"·"할 일" 같은 **단어 자체**는 분류 용어가 아니라 사용자의 일상 언어다 — 캘린더·검색 필터에 그대로 쓴다.
- 모찌가 분류를 확신 못 할 때(needs_review)만 예외적으로 확인을 청하되, 그때도 라벨 검수가 아니라 행동 후보 선택으로 묻는다.

## 6. 비기능 요구사항

### 성능
- 홈 첫 로딩: 2초 이내
- 메모 저장 응답: 즉시 저장 후 비동기 분석
- 이미지 분석: 비동기 처리
- 질문 응답: 5~10 초 이내
- Share Extension 저장: 사용자가 오래 기다리지 않도록 큐 처리

### 보안
- OAuth 기반 인증 (JWT RS256)
- 이미지 URL private access
- 사용자별 데이터 격리
- 민감한 원본 데이터 암호화 고려

### 개인정보
- 사용자가 원본 삭제 가능
- AI 분석 결과 수정 가능
- 데이터 내보내기 가능
- 계정 삭제 가능
- AI 분석에 어떤 데이터가 사용되는지 안내

### 접근성
- Dynamic Type 대응
- VoiceOver label 제공 (아이콘 탭 포함)
- 색상만으로 Intent 구분하지 않기
- 충분한 대비

## 7. 주요 리스크와 대응

| 리스크 | 설명 | 대응 |
|---|---|---|
| Share Extension 제약 | 앱 본체와 실행 환경 다름 | App Group, 서버 큐 설계 |
| 백탭 설정 복잡 | 사용자가 직접 설정 필요 | 온보딩에서 단계별 안내 + 실동작 검증 |
| AI 오분류 | 일정/할 일 잘못 분류 가능 | 확신할 때만 능동 등록(needs_review 면 확인 청함), 제목 인라인 교정 제공 |
| 이미지 분석 비용 | 스크린샷 분석 비용 증가 | 압축, 비동기, 모델 라우팅 |
| 링크 Fetch 실패 | 일부 앱/사이트 제한 | 메타데이터 fallback |
| 개인정보 우려 | 스크린샷에 민감정보 포함 | 명확한 삭제/비공개 정책 |
| 질문 답변 환각 | 없는 기록을 말할 수 있음 | 반드시 근거 모찌 표시 |

## 8. UX 원칙

> 사용자가 정리하게 만들지 않는다.
> 사용자는 보내기만 하고, 모찌가 정리한다.

핵심 버튼은 "추가하기" 가 아니라:
- 맡기기
- 저장하고 정리하기
- 모찌에게 보내기
- 캡처하고 정리하기

**분류는 보여주는 것이 아니라 작동하는 것이다** — 사용자에게 중요한 것은 "어떤 일정이 언제, 뭘 해야 하는지, 언제 다시 알려주는지"이지 모찌가 내부에서 몇 가지로 분류했는지가 아니다 (§5 노출 원칙).
